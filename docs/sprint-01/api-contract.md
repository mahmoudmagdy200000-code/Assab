## Evidence and common contract rules

* **Legacy shift API:** explicitly registered aliases begin `/api/` and `/api/v1/`; each full route is listed in [route-map.md](route-map.md#full-registered-route-records). Shared identity middleware is Sanctum plus route-specific cashier, branch-manager, or branch-manager-or-cashier middleware; resource ownership/branch checks also happen in handlers. `LogThrottledRequestsMiddleware` is request logging; do not read it as rate limiting.
* **Company API:** company routes use `/api/v1/company/me/...` and some have an additional `/api/...` alias. They use Sanctum, `ResolveTenant`, `IdempotencyKey`, and `AuditMutations`; nested role middleware is on route groups. Current registrations include branch open/close and accountant close (`Modules/Admin/routes/api.php:434, 480-484, 853-857, 923-924`). Company scope derives from authenticated tenant/role; do not assume legacy branch middleware provides tenant isolation.
* Unless a handler returns an explicit code, Laravel JSON responses default to **200**. These are static code-derived response codes, not HTTP-tested status codes. Auth middleware is expected to reject unauthenticated calls (normally 401) and role/ownership checks return 403; exact envelope from middleware is **REQUIRES VERIFICATION**.
* The legacy `successResponse` handlers return a success/message/data-style envelope; some use raw `response()->json`. Error envelopes vary between `{success:false,message,errors?}` and `{success:false,message}` or BaseController output. There is no single verified error schema. Validation is commonly inline `Validator`, not a FormRequest; `Modules/Shift/Http/Requests/EndShiftRequest.php` is not used by the end route (`route-map.md`, “end”).
* Monetary unit rule: legacy CashierShift monetary casts/resources are decimal SAR (`Modules/Shift/app/Models/CashierShift.php:54-62`; `Modules/Shift/app/Transformers/ShiftDetailResource.php`); API names generally do not encode unit. Company API fields explicitly named `*Halalas` and Dashboard types use integer halalas (`dashboard/artifacts/mockup-sandbox/src/api/queries/shifts.ts:113-160`, `dashboard/artifacts/mockup-sandbox/src/api/types/company.ts:763-795`, `dashboard/artifacts/mockup-sandbox/src/api/money.ts`). Flutter models use `double` or parse integer values; neither is an authoritative unit declaration. Any unspecified unit below is **UNKNOWN**.

## Endpoint contracts

### L1 — Start cashier shift

* **Method / URL:** `POST /api/cashier/shifts/{shift}/start`; alias `POST /api/v1/cashier/shifts/{shift}/start`. Manager-start alternative: `POST /api/branch-manager/shifts/start-by-manager/{shiftId}`; alias `POST /api/v1/branch-manager/shifts/start-by-manager/{shiftId}` (`Modules/Shift/routes/api.php:335-336, 157-159`). Each alias is a separate registration; middleware differences are listed in route-map.
* **Authentication / scope:** Sanctum; cashier middleware for self-start; cashier must own the scheduled shift. Manager-start is branch-manager route group and handler validates branch/scheduled shift (`CashierShiftController::startShift` around lines 299-343; `startShiftByManager` around 886). Tenant middleware is not present on L routes.
* **Request:** path ID only; no body fields. Amounts: none.
* **Validation/state:** shift must be `NOT_STARTED` or `REASSIGNED`, scheduled date today; manager-start is for an eligible pending cashier shift. Exact manager handler conditions should be verified against its full source before implementation.
* **Response/errors:** source success envelope contains `ShiftDetailResource` and progress; static default success 200. Invalid state 400; missing/inaccessible shift 404; auth/ownership 401/403; caught exceptions may be 500. Runtime status/envelope **NOT VERIFIED**.
* **Effects/retry:** status/start timestamp and related shift start effects; transaction/row locking/idempotency not established (**UNKNOWN**). No L idempotency middleware.
* **Consumers:** Flutter `shift_management_remote_data_source.dart` has manager-start call around line 160; Dashboard uses Company open route instead.
* **BR/AC/Sprint:** BR-12; AC-12/13; A09/A10. **AS-IS:** start can be a state flip independent of a receipt confirmation. **TO-BE:** shift opening cash must derive from confirmed receipt; settings alone is not proof. **GAP:** opening source and zero/omitted behavior are not contractually represented here.

### L2 — End cashier shift without handover

* **Method / URL:** cashier: `POST /api/cashier/shifts/{shift}/end` and `POST /api/v1/cashier/shifts/{shift}/end`; branch-manager group: `POST /api/branch-manager/shifts/{shift}/end` and `POST /api/v1/branch-manager/shifts/{shift}/end` (`Modules/Shift/routes/api.php:353-354, 174-175`).

* **Request:** `total_sales` required numeric >=0; `cash_collected`, `card_payments` optional numeric >=0; `aggregators[]` optional, each `aggregator_id` required/existing and `amount` required numeric >=0, optional notes string <=255; optional `pos_receipt` JPG/JPEG/PNG/PDF <=5120 KB; optional `variance` object: `responsibility_type` in `self|self_and_others|other_factors|mixed`; `current_cashier_amount` required for self_and_others/mixed; `other_cashiers[]` IDs and nonnegative amounts; notes <=255; reason conditionally required <=500; supporting files PDF/PNG/JPEG/JPG <=5120 KB. Aggregator IDs are checked unique. No independent `counted_cash` request field. Numeric amount units are not encoded; legacy model/resource indicates decimal SAR. Null/omitted channel semantics are inconsistent (optional/default zero), and must be preserved until agreed.
* **Response/errors:** success includes `shift` resource, `variance`, and `summary` with total/net/VAT/sales breakdown/opening balance/handover status and next actions (controller around 147-187). Static success 200; validation 422; missing/inaccessible 404; wrong state 400; caught exception 500. Error shape differs by branch. HTTP behavior **NOT RUNTIME VERIFIED**.
* **Effects/transaction:** ShiftEndService writes completed state, end time, sales/VAT/net, receipt/breakdown/history in a DB transaction; optional custody posting and variance detail/file recording occur outside that service transaction or in separate transactions. Observer/event bridge may synchronously update Admin projection. No idempotency middleware or durable command key. Details in `route-map.md` “end”.
* **Consumers:** Flutter multipart `EndShiftRequest` calls manager end route (`AssabAPP/lib/features/shift_module_features/shift_management/data/data_source/shift_management_remote_data_source.dart:119-129`; model `.../end_shift_request.dart:8-70`). Dashboard shift hooks do not post this endpoint; Dashboard consumes company shift projection and operation queue.
* **BR/AC/Sprint:** BR-01–04, BR-07–11, BR-25; AC-01–06, AC-21; A01–A05/A18. **AS-IS:** legacy VAT calculation uses total×15%, variance uses total less reported channels, and no separate count is accepted (route-map “end”; `ShiftEndService.php:185`, `CashierShift.php:212-219`). **TO-BE:** gross VAT-inclusive; net=gross/1.15; expected cash=gross−cards−apps+confirmed opening; variance=counted−expected; complete approved shortage allocation required before report closure; surplus belongs to branch. **GAP:** formula/sign, missing counted amount, optional/partial allocation and transaction boundary conflict with approved rules.

## Contract-breaking risks to resolve before implementation

1. Converting legacy numeric SAR to halalas without explicit versioned conversion or precise rounding changes existing clients’ values by 100×.
2. Replacing/requiring `cash_collected`, `handover_amount`, or accepting new `counted_cash` without preserving current Flutter multipart behavior breaks existing requests.
3. Renaming Flutter `to_branch_manager` to backend `branch_manager_id`, or changing handover response nesting/status values, is a wire break.
4. Changing end from terminal report completion to a separate submitted/review state can break consumers that infer finality from `shift.status`.
5. Tightening null/omitted/zero behavior can break the Flutter request, which omits some zero-valued payment fields; zero must remain distinct from missing.
6. Changing 200/400/422/409 or error envelope shapes can break client error handling; these are currently code-derived, not integration-tested.
7. Adding tenant/role checks to L aliases may reject clients that currently rely only on cashier/manager identity; preserving unauthorized access is not an option, but rollout needs compatibility planning.
8. Replaying/duplicating close, submit, approve, reject, or receipt actions can duplicate financial effects; current legacy routes lack explicit idempotency and Admin key scope/replay semantics are insufficiently bound.
9. Flattening legacy and company routes into one DTO risks mixing tenant models, role assumptions, persisted shift records, and money units.
10. Approval of an expense through both direct route and bridged Dashboard operation can create conflicting decisions unless one authoritative path is selected.

* Legacy request fields `total_sales`, `cash_collected`, `card_payments`, aggregator `amount`, `handover_amount`, variance shares/counts, `opening_balance`, and daily-close totals have no unit suffix. Legacy casts and Flutter `double` imply SAR, but contract does not expressly promise this.

### 3. Final money contract and open edge decisions

Canonical calculation/storage boundary for new financial decisions is signed integer halalas. Existing legacy API fields remain decimal SAR JSON numbers for compatibility; validators first convert their decimal text to integer halalas exactly once. Admin `*Halalas` inputs/outputs remain integer halalas with no conversion. No blanket `×100`/`÷100`: only named SAR↔halalas adapters convert. Legacy SAR response fields are serialized from integer halalas as fixed two-decimal values; Admin fields remain integers.

| Decision | S1-05 choice | Rule / effect |
|---|---|---|
| Gross/net/VAT | Gross includes VAT. `netHalalas = round-half-up(grossHalalas × 100 / 115)` for nonnegative gross; `vatHalalas = grossHalalas − netHalalas`. Round once at the net extraction boundary; VAT is residual. | Exact BR-01 formula and preserves gross = net + VAT. Integer quotient/remainder implementation; no floating point. 11,500 → net 10,000, VAT 1,500. |
| Input precision | SAR inputs accept at most two fractional decimal digits; reject excess digits (422), never round input. Halala inputs must be JSON integers. | Covers one halala. No exponent notation, NaN, Infinity, locale separators, or binary-float conversion as source text. |
| Maximum | Per nonnegative amount: 999,999,999,999 halalas = SAR 9,999,999,999.99. Signed derived values may range −999,999,999,999…+999,999,999,999 halalas. Validate before arithmetic and aggregate totals against same ceiling. | This fits signed PHP integer and JavaScript safe-integer budgets and current DECIMAL(12,2) legacy columns; if any deployed column is narrower, implementation must use the smaller schema limit and block pending an ADR revision, never overflow/truncate. |
| JSON wire | Preserve legacy SAR numbers for existing field names; exact input validation parses original decimal token/string without float intermediary. New clients should send decimal strings for new SAR evidence fields. Preserve Company/Admin `*Halalas` as JSON integers. | Avoid breaking old Flutter DTOs while defining exact new contracts. Dashboard JS number is safe for the selected halala maximum after safe-integer validation. |
| Null and zero | Input omitted/null = no evidence/unknown, not a monetary zero. Explicit `counted_cash: "0.00"` is measured zero. Opening amount is null until a receipt is confirmed; a confirmed receipt amount may be zero and must carry confirmed state and immutable receipt ID. | No settings fallback into confirmed opening, no defaulting to zero, and no loss of nullable presenter fields. |
| Non-cash movements | Expenses never reduce cashier expected cash. Expected cash = gross − cards − apps + confirmed opening. No unexplained clamp-to-zero; input channel totals above gross fail validation or require a separately approved movement type. | Consistent with BR-03/04; preserves a negative result only if a future explicit movement rule permits it. |

Mandatory vector: gross 11,500, cards 5,000, apps 2,500, confirmed opening 1,000, counted 3,000 halalas → net 10,000, VAT 1,500, expected 5,000, variance −2,000, shortage 2,000. Physical count already includes the opening present in drawer; opening is added to expected exactly once and never added to count. `cash_collected` remains the cash-channel sales figure and is not the physical count.

### 4. Counted cash and R02 bridge contract

**AS-IS:** legacy end accepts `cash_collected` (sales channel) but no independent drawer count. `BridgeLegacyCashierShift` currently synthesizes Admin `cashActualHalalas` as cash-collected plus opening float. AssabAPP request models omit counted cash and use decimal-like Dart doubles. This current bridge value is not count evidence and does not close R02 at runtime.

**TO-BE adapter:** retain the old field names/response envelope. A compatible client must submit a separately captured count in a new explicit `counted_cash` field (SAR, max two decimals) or versioned equivalent. Map only that field to Admin `cashActualHalalas`; map `cash_collected` only to cash-channel sales. Do not silently reinterpret `cash_collected`, `closing_balance`, `handover_amount`, an opening setting, or an omitted value as count. A client with no count cannot close a financial report: return 422 `COUNTED_CASH_REQUIRED`, preserve the unfinished state, and tell the client which field is missing. No guessed fallback.

**Client impact / GAP:** Dashboard already supplies `cashActualHalalas` and is compatible if it sends independently counted drawer cash. AssabAPP cannot satisfy this contract from its current payloads; it needs a future explicit client change or the business owner must approve a separately named legacy exception with its own non-acceptance status. S1-05 does not authorize that exception or Flutter work. Do not claim compatibility closure.

### 5. Stable report, revision, request, receipt, and history identity

Use the stable cashier shift/report aggregate identity as the report owner; each committed report revision gets an immutable UUID and monotonic per-report revision number. This applies to end-only legacy reports, reports with handovers, and native Admin shift reports. A report revision exists independently of any handover request. A report revision has zero, one, or multiple independently identified handover requests. Each request references exactly one source report revision and retains its own UUID/recipient/requested amount. Never fabricate a handover for an end-only report. Later handover request attaches to the then-current report revision.

Correction after rejection appends revision N+1 on the stable report aggregate. Old revisions and request links remain immutable; a request may be explicitly superseded/reissued against the new revision, but its old identity and rejected decision remain. Current lookup must use a locked aggregate pointer or unique max committed revision, never unordered `first()`. If legacy data resolves to multiple possible current requests/parents, fail closed and require reconciliation. A stale decision against a superseded revision returns 409 and has no effects.

Each confirmed physical receipt has its own immutable receipt UUID, request UUID, source revision UUID, exact recipient actor, receiving shift/custody UUID, confirmed amount, confirmer, timestamp, evidence/attachment references, and one stable movement identity. Partial receipt confirms a nonnegative amount no greater than the outstanding request/responsibility; sender retains requested/owed minus cumulative confirmed amount. Receipt identity is independent of report revision; later report corrections cannot rewrite receipt amount, recipient, time, or ledger movement. Corrected reports must explicitly reconcile against already confirmed movements; any impossible total is 409 `CONFIRMED_RECEIPT_CONFLICT`, with old receipt and report history retained.

Retain revisions, rejection reasons, employee responses, manager approvals, receipt evidence, and attachment object references for the report's financial retention lifetime; corrections append, never delete/replace. Attachment deletion or unavailable object storage is surfaced as an evidence integrity error and cannot silently erase the referenced evidence. No automatic report/receipt/attachment purge is allowed by these commands.

### 6. Receipt-to-opening rule

The receiving custody identity is the scheduled cashier shift UUID (or native company shift UUID for that route generation), paired with the authenticated recipient identity and branch. `receiving_shift_id` is mandatory for positive receipt and must belong to the exact named recipient in the same branch. A stable receipt UUID and stable business-effect key `receipt:{receiptUuid}:opening:{receivingShiftUuid}` provide exactly-once application. Opening is the sum of distinct confirmed receipts explicitly assigned to that one receiving shift, with a separate `openingConfirmed` evidence flag; absent receipt gives null/unconfirmed, confirmed zero gives 0/confirmed.

Repeated reads return the same receipt-derived opening; retrying confirmation with the same key/payload returns its original response. A receipt cannot be applied to another shift, even for the same cashier. Correction never edits or moves the receipt; a reversal requires a separate authorized, linked compensating financial fact, not mutation. No configured settings fallback. Example: requested 6,150, confirmed 6,100 → new opening 6,100; prior 50 remains under preceding responsibility. A later duplicate confirmation creates no second opening or ledger movement.

### 7. Shortage liability authority and state guards

Persist and expose separate facts/states: physical custody request/receipt; calculated shortage/surplus; provisional allocation; sending cashier's complete-allocation confirmation; each employee's acceptance/objection; branch manager's final approval for the current revision; accountant's reporting/review. No one state implies another. Allocation shares must total the complete negative variance, and employees must belong to the same branch. A manager may receive an allocated share and must approve their own share explicitly as the authorized manager. Employee objection requires reason and remains visible, but never blocks handover. No automatic payroll deduction. Surplus is branch-only and not an employee liability.

Mutation guards: only the report owner creates allocation; only the named employee records their own response; only authorized branch manager for report branch gives final approval; accountant cannot create/finalize employee liability; each command carries current report/allocation revision. First valid decision on current revision wins. A correction invalidates pending allocation/approval for the previous revision but preserves it historically. A receipt command remains independent of employee or manager liability decisions.

### 8. Daily submission guard (design only)

**Current path:** `BranchManagerShiftController::submitDailyReport()` via `POST /api[/v1]/branch-manager/workday/daily-close/submit`, `auth:sanctum` + `branch.manager`. Current source checks completed own-current-day manager shift and duplicate submission, but not current cashier-report revisions, full allocation, cashier confirmation, employee response, or manager liability approval. It writes submission flags and marks handovers in a transaction then dispatches the daily event. S1-05 makes no code change.

**Exact target predicate:** before daily-submit mutation, lock the manager workday and included report aggregates in deterministic order; require each included report to be completed and point to its current committed revision. For every negative variance require count and confirmed-opening evidence, exact full in-branch allocation, sender's complete-allocation confirmation, and the same-branch branch manager's final approval for that exact revision/allocation (including a manager's own share). Positive/zero variance needs no liability approval; surplus remains branch-only. Receipt confirmation is not a report-submit prerequisite; unreceived cash remains sender responsibility. If any predicate fails, return 409 with `LIABILITY_APPROVAL_REQUIRED` or `STALE_REVISION`, perform no submit/receipt/ledger changes, and include the affected report/revision identifiers in the existing error envelope. Authorize only the branch manager for the manager's own branch workday. Re-read all predicates under lock before writing submit marker and daily-close links atomically.

### 9. Idempotency, replay, and business-effect uniqueness

Every financial/state mutation requires `Idempotency-Key` (opaque UUIDv4); GET/read paths do not. Authenticate and authorize before replay lookup. Scope the request record by `(tenant/company, branch, actor type + actor ID, HTTP method, normalized route/command, resource ID, target revision ID, key)`. Canonical payload includes normalized accepted fields, explicit null/zero distinction, sorted object keys, stable attachment IDs/content hashes, and excludes transport-only fields. Store hash and response status/body.

Reserve key atomically before effects. Same scoped key + same payload while processing returns 409 `IDEMPOTENCY_IN_PROGRESS` and `Retry-After`; completed request returns the original status/body. Same key + changed canonical payload returns 409 `IDEMPOTENCY_KEY_REUSED`. Lost response is recovered by same key/payload. Cache record retention is at least 90 days and never shorter than a client retry window; after expiry a replay may execute only if the independent business-effect identity permits it. Keys are not a financial uniqueness constraint.

Permanent business identities/unique constraints (or locked equivalent) remain beyond cache TTL: one report revision per `(report aggregate, revision number)`; one exact recipient decision per allocation/revision/actor; one receipt confirmation per immutable receipt UUID; one opening application per `(receipt UUID, receiving shift UUID)`; one source-effect per `(source aggregate, source revision, effect type)`; one Admin mirror per legacy source UUID/revision/effect; one daily submission per workday/revision. Same effect under a different request key is a business duplicate and returns its existing result without posting again. Attachment identity participates in canonical payload and retention but does not replace receipt/effect uniqueness.

### 10. Transaction, lock ordering, retries, and writer authority

Target sequence for each mutating command: (1) authenticate/authorize; (2) validate syntax/shape/units; (3) begin DB transaction; (4) acquire idempotency reservation; (5) lock rows in global order: tenant/branch scope → stable report aggregate/workday → report revision → handover request/allocation → receipt/effect identity → custody balance/ledger account → Admin mirror/operation; sort multiple IDs lexically; (6) re-read state/current revision and authorization scope; (7) reject stale/invalid state; (8) calculate with integer halalas; (9) append immutable report snapshot/revision; (10) write authoritative financial state, receipt/opening, ledger, audit and idempotency response; (11) commit; (12) return stored response; (13) only then emit notifications/cache invalidation/search/read projections.

Required financial facts MUST share one commit: report totals + revision + confirmed count/opening references; receipt + sender/receiver custody movement + receiving opening + business-effect identity; shortage allocation/response/final approval + immutable audit; daily submit marker + included revision links + audit; Admin financial close + operation/snapshot/ledger fact + replay result. Do not catch-and-log an essential write failure and commit the parent fact. Projection/notification failure after commit is retryable and cannot create a second financial effect. Outbox rows, if selected, are inserted in the same commit; dispatch is after commit.

Retry deadlocks/serialization failures at most three times with bounded jitter, re-running the full transaction and all locked-state checks; never retry a domain conflict. Return 409 after exhaustion with a retryable code and no partial facts. Concurrent first decision wins; the loser re-reads and returns same-key replay or 409 stale/conflicting state. Lock order is mandatory to reduce cycles; DB unique constraints remain the final duplicate barrier. Lock strategy/DB isolation must be validated against the deployed DB before implementation.

Writer map: legacy report revision is the authoritative report fact; Admin `asab_shifts` is a compatibility projection unless the command originates natively in Admin. The recipient confirmation command is sole writer of immutable receipt fact. Receipt-opening application is sole writer of confirmed incoming opening. One canonical cash movement ledger writer per source effect is authoritative; event listeners/observers may project/read but cannot write a second equivalent effect. Legacy bridge uses outbox/source-effect uniqueness and is not a second authority. Admin mirror rows are explicitly projections with source UUID/revision and unique effect identity. Shift totals, variance, handover request, receipt, opening, ledger movement, and Admin projection each have one named writer; remove/disable duplicate listener financial effects in S1-08/S1-11 as needed.
