## Authorized S1-10 changes

1. **A1 / R2a / R2b / C1:** work can start before the predecessor's report or receipt. A started predecessor keeps its existing `cashier_shifts` row, report aggregate, counts, allocations, sales channels, requests and evidence. An empty incoming `cashier_shifts` row uses the existing schema and unique schedule key. Both rows are linked by history (`reassignment_work_assigned` / `reassignment_report_separated`). No financial data is copied. Reassign response `data.shift.id` is the incoming work/report ID; `data.source_cashier_shift_id` is the predecessor ID. Clients must use the returned work ID; client release compatibility remains an open gate.
2. Operational accept/start changes only the incoming row. Start creates no receipt, opening, or liability and does not financially close the predecessor. A counted predecessor retains the existing `REASSIGNED` submitted-report fact; an unreported predecessor remains `IN_PROGRESS` and may report later. Financial writers recheck the current row owner; the incoming cashier cannot overwrite the predecessor. `REASSIGNMENT_SPLIT_REQUIRED` is retained only for an unseparated legacy financial report, never as a work-start prohibition. Legacy shared rows can separate inside locked accept/start. An existing incoming schedule row causes a conflict, never overwrite/reuse of another report. A rejected independent work assignment cancels only the empty incoming work row and preserves the predecessor's report/shortage.
3. **R1 / confirmed P1:** `shifts:auto-end-overdue` remains the scheduler entry point but only logs overdue status and sends an in-app reminder. It writes no status, end timestamp, count, shortage, receipt, or financial operation. It cannot dispatch financial completion/bridge because time elapsed. The report remains open for actual submission. Repeated scheduler runs may repeat reminders; no new notification lifecycle is introduced.
4. **A3 / C4:** failed rejection uploads are cleaned up using only paths generated by that attempt, including partial upload failure. Existing evidence is untouched. Conflict checks stay before upload. A committed attempt's files are retained. This covers manager rejection, recipient rejection, and operational reassignment rejection.
5. **C2 / R3c:** preserve historical source-branch attribution, actual-start requirement and deterministic tie-ID ordering.
6. **C3:** preserve shift-then-approval `lockForUpdate`, fresh state/recipient checks, and financial owner checks. **MYSQL CONCURRENCY = NOT_RUN** until separate-connection MySQL testing is actually performed. SQLite sequential tests do not close this gate.

## R3b investigation only — physical return

Trace inspected:

- `ShiftTransferReceiptService::rejectManagerCashTransfer` records attempted physical cash and rejection reason, then creates immutable `ShiftTransferRejectionEvidence`.
- `HandoverService::rejectHandoverForAmountCorrection` records the same physical amount evidence for a cashier request. Plain recipient/manager rejection stores reasons/files and reopens the sender report; it does not establish physical return.
- `ShiftTransferRejectionEvidence` and its migration contain request/source/destination, requested/physical amounts, correction reason and rejected timestamp. No explicit returned amount, return timestamp, current-possession fact, or structured return-evidence link was found.
- `ShiftCashCountService::pendingIncomingHalalas` selects latest evidence per request, attributes the historical source branch to the appropriate started receiving shift, and excludes confirmed receipts. It has no explicit physical-return exclusion.
- Free-text reasons or attached files could describe return, but no typed writer/reader was found that uses them to establish a return fact in the cash equation.

**Result:** the inspected implementation cannot explicitly distinguish rejected-but-retained cash from rejected-and-returned cash. This is a trace gap, not proof that a specific transfer was physically returned or double charged. `status=rejected` alone proves neither return nor continued possession. `pendingIncoming` is unchanged. Business rule: evidenced physical return contributes zero recipient pending/opening and leaves responsibility with the sender. Return representation and the resulting correction are deferred for review before implementation.
