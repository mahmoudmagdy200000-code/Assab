# S1-04 — Cash-cycle states, permissions, and revision invariants

**Status: Ready for review; not Accepted.** This is a source-backed design contract only. It does not add runtime states, enforce permissions, or authorize a migration. S1-01, S1-02, and S1-03 remain Ready for review; not Accepted. S1-05 has a separate proposed blueprint and awaits Mahmoud design review; S1-06 remains blocked.

## 1. Scope and evidence rules

Current controllers, middleware, models, services, migrations, routes, policies, observers/listeners, and existing tests establish **AS-IS**. Business Rules v2.0 establish approved **TO-BE**. Proposed states and invariants below are target concepts, not existing fields or deployed behavior. The Sprint Plan assigns this task the state/permission matrix, revision invariants, and the minimal daily-submit liability guard; implementation belongs to later tasks.

The state contract applies to the legacy mobile cashier workflow and identifies the separate native Admin shift workflow where it intersects. They are distinct route and money contracts. In particular, R02 remains **PARTIALLY RESOLVED**: `cash_collected` is a sales-channel value, while the legacy bridge synthesizes Admin actual cash from `cash_collected + opening_balance`; that synthesized value is not independent physical-count evidence. The 115/50/25/10/30 application path remains **NOT RUN**. No transition below may claim physical-count evidence merely because the legacy value was bridged.

R05 remains **PARTIALLY RESOLVED**: the handover UUID is only a candidate request identity; duplicate/cardinality preflight has not run; there is no runtime revision/receipt schema; endpoint-specific idempotency and retry decisions belong to S1-05. This design does not rely on one handover row per shift or on the proposed unique index already existing.

### Business-rule anchors

| Rule | State/permission invariant used here |
|---|---|
| BR-05–06 | Report submission, receipt confirmation, and final shortage-liability approval are independent facts. Report submission alone does not transfer cash responsibility. |
| BR-07–08 | A default cashier assignment is provisional; the entire shortage must be allocated to employees within the branch and explicitly confirmed before report closure. |
| BR-09–10 | Branch manager is target final liability authority before daily submission, including self-allocation. Employee acceptance/objection is recorded separately; objection does not block physical handover and is not payroll authorization. |
| BR-11 | Positive variance is branch surplus; it creates no employee allocation or extra approval and does not increase sales. |
| BR-12–14 | Opening derives only from amount actually confirmed by recipient; configured float is not receipt. Corrected request amount precedes confirmation; only confirmed amount moves. |
| BR-15–17, BR-24 | Correct report data after rejection without erasing prior versions, evidence, or confirmed movement; no fixed rejection cap or recipient override. |
| BR-25 | Duplicate/concurrent attempts must not create duplicate financial effects; operation identity and replay details are deferred to S1-05. |

## 5. Revision and evidence invariants

The following are required target invariants. S1-04 defines them independently of any unverified shift-level unique index or not-yet-authored table.

1. **Aggregate/request identity:** report aggregate is `(source_kind, source_shift_id)` or FK-safe equivalent: legacy cashier shift or native Admin shift, with an Admin mirror resolving to the legacy aggregate. Existing `cashier_shift_handovers.id` is only a candidate stable request UUID. Each request points to exactly one source report revision; it is not a report parent or proof of one request per shift.
2. **Revision identity/current lookup:** proposed identity is `(report_aggregate_id, revision_number)` plus immutable revision UUID. Before first submit, aggregate revision is `0` with no revision UUID. First submit requires `expectedRevision: 0` and creates revision `1`. Correction requires the current positive number and appends N+1. Aggregate pointer/highest committed number is authoritative; no unordered request `first()` may select current report. Zero requests is valid; ambiguous request lookup fails closed.
3. **Supersession:** report correction after rejection creates revision N+1 on the same aggregate. Prior report revisions and request/receipt identities remain immutable. An unconfirmed old request is rejected/superseded; corrected custody intent receives a new request UUID on N+1. Confirmed receipt retains its original request/revision and ledger effect. “Current” and “superseded” are target semantics, not existing fields.
4. **Stale decisions:** every new decision targets an explicit report revision and, where relevant, request/allocation ID. A new decision for a superseded revision conflicts without financial effect. After authorization, a completed same-key/same-payload retry replays its stored result before a stale check; it is not a new decision. Transaction enforcement belongs to later implementation.
5. **Snapshot contents:** retain submitted totals and channel breakdown; count evidence/source and opening evidence; request/recipient/amount; allocation rows; employee responses; manager decision; rejection reasons; actor identity/type/time; and stable attachment references. The proposed snapshot table is described in `schema-adr.md`; it is not deployed.
6. **Attachments and rejection reasons:** correction does not delete prior file objects or overwrite old rejection reasons. Retain the actor, time, reason, and attachment reference on each historical revision. A DB path alone does not prove that the object remains stored.
7. **Allocation preservation:** allocations and each employee response attach to a specific revision. A later correction creates a new allocation state; it cannot change a confirmed receipt or prior ledger movement.
8. **Receipt and custody:** only recipient confirmation of the exact valid request amount records a receipt. A partial *custody transfer* is an intentional request for part of outstanding responsibility, confirmed exactly; sender keeps the remainder. Mismatch against an unchanged request requires rejection and correction. Confirmed receipt and its ledger movement are immutable and cannot be replayed by correction.
9. **No inferred evidence:** settings/default float, zero defaults, request amount, approval status, `handed_over_at`, Admin projection, or synthesized bridge actual cash do not establish a confirmed receipt or independent physical count.
10. **Conditional database uniqueness:** proposed `UNIQUE(report_aggregate_id, revision_number)` identifies report revisions; a request has one immutable source revision and at most one confirmed receipt. No one-row-per-shift assumption is approved. Permanent receipt effects are unique by `(tenant/company, branch, request UUID, effect type, destination custody/shift identity)`. Any constraint/backfill requires S1-03 duplicate/cardinality preflight and review; none ran here.

## 6. Daily-submission liability guard

### Current trace

The registered legacy endpoint is the branch-manager workday daily-close submit route in `Modules/Shift/routes/api.php:228-270`, under `auth:sanctum` and `branch.manager`. `BranchManagerShiftController::submitDailyReport()` validates only optional `final_notes`, selects the authenticated manager’s own branch-manager shift for today with `status=completed`, rejects an already-submitted daily report, then transactionally sets `daily_report_submitted`, timestamp, notes and `can_reopen`; it marks included approved handovers daily-closed and dispatches `DailyReportSubmittedEvent` (`Modules/Shift/app/Http/Controllers/BranchManagerShiftController.php:730-780`). This branch daily-submit state is distinct from the cashier shift’s `completed` end/report state; current cashier source has no separate revision-bound submission flag.

It does **not** inspect the underlying cashier shift’s current revision, variance, complete allocation, assigned employee branch membership, cashier completeness confirmation, employee responses, or a distinct branch-manager final-liability approval. Therefore a cashier-shift shortage can currently reach daily submit without the BR-08/09 target guard. Route middleware limits actor role; own-branch-manager-shift lookup limits workday identity; neither supplies the missing financial-state gate.

### Minimal target guard (design only; do not implement in S1-04)

`requiredHandovers` is server-derived from the shifts/reports included in this branch/workday daily-close scope and their associated incoming/outgoing transfers. Every required valid request must reach the existing `confirmed` receipt condition. Rejected/superseded requests retain history; the corrected replacement must complete confirmation, rather than treating rejection as successful completion. Unrelated pending branch transfers outside this set do not block this day. No new states are introduced. This completion gate applies even to balanced/surplus reports and even after shortage liability is approved. Shift report submission itself remains allowed with a pending incoming transfer. See API contract §8; runtime enforcement is S1-07, with S1-10/S1-11 evidence integration.

The actual server trigger is `POST /api/v1/branch-manager/workday/daily-close/submit` (plus legacy alias). No current AssabAPP or Dashboard caller invokes it: the app button changes local state only. App wiring is future week-two work; the S1-07 server guard still must be implemented and tested. `workday/end` and `PUT workday/daily-close` do not submit the day.

The server derives the included report set by branch and workday date. AS-IS includes approved handovers carried for up to seven days (`BranchManagerShiftService.php:292-320`). A client `includedReportRevisions` vector is only a staleness check and must equal this derived set. Reopen clears the submitted state for the same set; resubmission recomputes the set and links each current report/revision once, reusing the daily operation identity to avoid double counting. Exact operation key/transaction design remains a technical proposal.

For every included report with a negative variance, permit daily submit only if all conditions hold for its **current report revision**:

1. Independent counted-cash evidence is present to establish variance. Confirmed opening is the sum of receipts and defaults to numeric zero when none exist; no confirmed-opening receipt is required solely to represent a no-cash shift. A legacy bridge-synthesized `cashActualHalalas` is not independent count evidence (carry-forward R02).
2. The entire shortage is allocated, sum exactly equals the shortage, and each responsible employee is currently in the same branch.
3. For original cashier submission, the cashier explicitly confirmed the complete allocation for that exact revision. For manager-correction revisions, do not require cashier re-approval of the correction or its resulting allocation; the same-branch manager may allocate the resulting shortage and perform the approved final liability action. A manager-sender shortage follows the same named-assignee/manager-final-approval responsibility rules without creating a separate manager-workday subsystem.
4. The branch manager authorized for that branch recorded final liability approval for the exact allocation and revision, including when personally assigned.
5. No rejection/correction has superseded the approved revision; otherwise require correction/resubmission/reapproval on the new current revision.

If any liability/staleness check fails, block daily submission without changing submitted flags, receipts, custody, ledger, or prior revision evidence. For zero or positive variance, no employee liability allocation/approval is required; positive surplus stays branch-only and accountant-reviewable (BR-11). Pending transfer does not block shift report submission; the sender remains responsible, cash physically present is counted, receipt remains pending (not surplus), and daily submission to the accountant waits for required transfer completion. Employee objection remains recorded and does not block handover. Daily submit requires branch-manager final liability approval for shortages, including manager-owned actual shortage, AND completion of all required transfers in the scoped daily-close set, regardless of variance sign.

**Minimality:** this is one server-side predicate over the authoritative current report/allocation revision and branch manager decision. It is not a new role, a substitute accountant approval, a UI workflow, or a general report-completion gate. Exact state fields/API response, transaction/locking and idempotency mechanics remain for S1-05 and implementation tasks.
