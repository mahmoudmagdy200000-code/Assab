## Registration and shared boundaries

Backend `bootstrap/app.php` registers `routes/api.php` with /api and prepends ParseMultipartFormDataMiddleware. `routes/api.php` scans module Routes/api.php and routes/api.php under apilocale, deduplicating real file paths within that loader. Shift's `app/Providers/RouteServiceProvider.php` independently registers `Modules/Shift/routes/api.php` with /api/v1. `php artisan route:list --path=api --json` registered both prefixes: 16 cashier shift routes and 39 branch-manager shift routes under each. Admin close routes register at `/api/v1/accountant/shifts/{id}/close`, `/api/v1/company/me/shifts/{id}/close`, and `/api/v1/company/me/branch/shifts/{id}/close`. Route names, aliases, and middleware can differ between these paths; the registration output does not establish request behavior. Admin routes include v1 and its provider uses /api, so both loaders can declare /api/v1 Admin routes. No duplicate core financial route signature was found in the documented map comparison.

`Modules/Shift/routes/api.php`: cashier group (286) auth:sanctum, cashier, log.throttle; branch-manager group (24) auth:sanctum, branch.manager.or.cashier, log.throttle; branch-manager/workday (226) auth:sanctum, branch.manager, log.throttle. Locale comes from the root loader alias, not necessarily the module-provider alias. log.throttle is request logging; it must not be assumed to enforce rate limiting. Legacy identity middleware checks active Cashier/BranchManager types; per-resource ownership/branch checks occur in controllers. No Admin tenant/idempotency middleware is declared on these legacy paths.

Admin middleware aliases in bootstrap: asab.tenant → ResolveTenant; asab.role → EnsureAsabRole; asab.idempotency → IdempotencyKey; asab.audit → AuditMutations. Routes use Sanctum authentication plus tenant/role boundaries. ResolveTenant requires AsabUser and resolves company/role assignments. Shift/Operation use BelongsToTenant global scoping; unresolved console/queue context may be unscoped, while resolved unauthorized context is denied. Accountant controller applies assigned-branch scope; branch-company controller derives its branch from signed-in role scope. These are distinct from legacy cashier identity. Do not infer company isolation from branch middleware alone.

Admin company/me routes declare idempotency/audit on the parent group and role on nested groups; runtime ordering/replay versus child authorization needs verification. IdempotencyKey currently looks up a global key and replays stored results, then persists successful responses after effects with a one-day expiry. No actor/route/payload identity check or pre-effect reservation was found there. Global unique key is not durable financial-command uniqueness. Accountant close alias does not explicitly declare this middleware. These findings belong to S1-09; no fix is made here.

### CURRENT TRANSACTION BOUNDARIES — AS-IS

This is source discovery, not a fix or an approval of current accounting behavior.

* **End without handover:** `ShiftEndService::endShiftOnly` begins a DB transaction at method entry, writes `cashier_shifts`, `shift_sales_breakdown`, and history, then commits at the method's main success point. On exception before commit it rolls back/rethrows. Its optional Total Sales custody write is after that commit; a caught custody failure cannot undo the completed shift. The controller later invokes `VarianceCalculationService::recordVariance` in a separate transaction; its detail/alert writes and file storage are not atomic with the first commit.
* **End with handover:** `ShiftEndService::endShiftWithHandover` opens an outer transaction and invokes end-only, handover recording and optional variance recording. Nested service `beginTransaction`/`commit` calls use Laravel transaction nesting; an inner commit does not commit the outer transaction. Catching an error rolls back the outer unit, but listener/file/custody work that runs before outer commit may have side effects outside the database transaction. In particular, the end-only post-commit code is only locally post-commit and still inside this outer transaction; its swallowed custody failure does not abort the enclosing call.
* **Record handover alone:** `HandoverService::recordHandover` wraps sender/handover/status/history writes in a transaction and commits before attempting Total Sales custody. When called beneath the end-with-handover outer transaction, this is a nested commit and the custody call occurs before outer commit. The custody error is caught/logged.
* **Cashier receipt accept:** `acceptHandoverByCashier` commits status, shift, opening and history writes; afterwards it attempts sender and recipient custody entries in a try/catch. The database decision can persist without either/both ledger rows.
* **Manager approval:** `HandoverService::approveHandover` transaction covers approval/status/variance/history writes and dispatches `HandoverApproved` before its commit. The synchronous personal-ledger listener therefore runs before the outer commit and catches its own errors; approval may commit without that row. Any notification/event behavior beyond these explicit listeners is not asserted as after-commit.
* **Variance ledger projection:** `VarianceRecorded` listener is queued with `afterCommit=true`, retries are configured, and the handler then uses its own transaction to replace variance ledger rows. Its exception path rolls back and logs without propagating to the original request. Queue exhaustion/retry outcomes were not runtime-tested.
* **Daily report submission:** `BranchManagerShiftController::submitDailyReport` commits its daily report/handover-close database transaction before clearing cache and dispatching `DailyReportSubmittedEvent`. A later listener/projection failure does not roll back the already-submitted report.

### Handover rejection and correction — AS-IS versus TO-BE

**AS-IS (`HandoverService::revertCashierShiftAfterHandoverRejection`, source lines 383–434):**

* If supplied, a generic `cashier_shift_history` row records `handover_rejected_shift_reverted` with before/after status and caller audit data. This is not a full report revision snapshot.
* `ShiftSalesBreakdown`, `ShiftVarianceAlert`, `ShiftVarianceDetail` (table `shift_variance_details`), `CashierShiftHandover`, and `ShiftHandoverStatus` are deleted through models with no `SoftDeletes` trait: those rows are hard-deleted.
* Linked `CashierCustodyTransaction` rows are deleted through `CashierCustodyService::deleteTransactionsForCashierShift`; that model uses `SoftDeletes`, so rows are soft-deleted. The helper failure is caught/logged and reset continues.
* `PersonalLedgerTransaction` rows for this shift with type `Variance from Cashier` are deleted through a `SoftDeletes` model, so those rows are soft-deleted. This call is not wrapped in the local try/catch shown for custody.
* The `cashier_shifts` row is updated to `IN_PROGRESS`; total/net/VAT, cash/card, closing/expected balance, variance become zero; `pos_receipt`, handed-over timestamp, notes, next cashier and actual end time become null.
* `CashierShiftHandover.variance_files` metadata is removed with the hard-deleted handover. Rejection uploads are placed under `handover_rejections` and paths can be kept in generic history audit; this reset does not delete those physical storage files. No file-deletion call is present in the inspected reset method.
* Custody history may retain soft-deleted rows; personal-ledger variance history may likewise remain soft-deleted. The reset does not prove preservation of old report values, attachment references or a confirmed receipt revision.

**GAP:** current reset hard-deletes operational detail/handover/status rows and zeroes report fields, while soft-deleted ledgers and orphanable uploaded files have different retention behavior. It is not compliant evidence of the target preservation contract. No changes are made here.
