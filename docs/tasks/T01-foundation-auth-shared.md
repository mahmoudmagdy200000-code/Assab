Scope reminder: `auth/*`, `auth/2fa/*`, `users/me/2fa-status`, `users/me/data-export*`, `users/me/account-deletion-request`, `auth/sso/*/callback`, `uploads/*` + `attachments/*`, `notifications/*` (shared + company copies), `lookups/*` (LookupController + CrossController), `search`, `exceptions`, and per-user prefs (`preferences|onboarding-state|saved-filters|quick-stats|table-prefs`). Response envelope note (load-bearing): ASAB endpoints do **not** use the SRS/NFR-1 `{success,message,data,meta}` shape. `Modules/Admin/app/Support/AsabResponse.php` returns a **bare** resource for single reads, `{data,meta}` for lists, `{error:{code,message,messageAr,details},requestId}` for errors (204 for no-content). This is an intentional, documented deviation ("the already-built frontend reads these exact shapes"). The FE-wiring `_TEMPLATE.md` header describing `{success,...}` is wrong for this project — the FE doc must document the real shapes.

## 2. Answers to critical checks

Critical checks derived from the assigned scope (NFR-2, NFR-8, NFR-9, §14.1, §4.8, §3). Each answered with file:line evidence.

1. **NFR-2 — is auth pinned to the `asab` guard and are the authed auth/* routes zero-trust?**
   Partial. A dedicated `asab` guard exists (`config/auth.php` L59-61 → provider `asab_users` → `AsabUser`, L112-114), but routes use `auth:sanctum` (routes L94), not `auth:asab`. The tenant/role groups (L113, L244) additionally run `ResolveTenant`/`EnsureAsabRole`, both of which reject non-AsabUser (`instanceof AsabUser`, ResolveTenant L22-27, EnsureAsabRole L18-22). **However** the routes directly under L94 — `auth/me`, `auth/logout`, `auth/change-password`, `auth/sessions`, `auth/2fa/*`, `users/me/data-export*`, `users/me/account-deletion-request` (L95-110) — have **only** `auth:sanctum`, no asab-guard assertion. Any principal holding a Sanctum PAT from a legacy guard (Supplier/Cashier/User all use `HasApiTokens`) satisfies `auth:sanctum` and reaches these handlers, which then assume an AsabUser (`AuthService::userPayload` L119-121 loads `roleAssignments`; `TwoFactorService::setup` writes 2FA columns). This is a zero-trust/NFR-2 gap → task T01.1.

2. **NFR-8 — are passwords/OTP/tokens hashed and never logged; credential emails via Notification module?**
   Mostly yes. Passwords use the `hashed` cast (`AsabUser` L31) and `Hash::check` (AuthService L43,149). 2FA TOTP secret is `encrypted`, backup codes `encrypted:array` + individually `Hash::make` (AsabUser L33-34; TwoFactorService L67, L127). 2FA SMS code is delivered via `TwoFactorCodeNotification` (notification channel, not logged; TwoFactorService L117). `two_factor_secret`/`two_factor_backup_codes`/`password` are in `$hidden` (AsabUser L28). **Gap:** password-reset email is **not** dispatched through the Notification module — `AuthService::forgotPassword` only writes the token row (L161-174), so the reset link never reaches the user via a real channel. No plaintext logging of secrets was found (the reset token is stored raw in `password_reset_tokens`, which is Laravel's standard, but is not hashed — minor).

3. **NFR-9 — idempotency on T01 mutations?**
   No for the shared surface. `asab.idempotency` is applied on the `admin` (L113), `company` (L483), support (L574) and `company/me` (L598) groups, but the shared group at L244 (`Route::middleware('asab.tenant')`) has **no** idempotency middleware. Therefore T01 mutations `uploads/presigned-url`, `uploads/direct`, `uploads/{id}/confirm`, `attachments/{id}/verify`, `attachments/{id}` DELETE, `notifications/{id}/read`, `notifications/read-all`, `auth/2fa/*`, `users/me/data-export`, `saved-filters` POST are **not** replay-protected. `IdempotencyKey` middleware itself is correct (only stamps on <300 responses, 24h TTL; IdempotencyKey.php L16-50) — it is simply not attached here. (Public `auth/login`/`refresh` are correctly outside idempotency.) → task T01.2.

4. **NFR-3 tenant isolation on lookups/search (foundation must not leak cross-tenant)?**
   Partial leak. Tenant scoping is enforced by the `BelongsToTenant` global scope (populated by `ResolveTenant`; BelongsToTenant.php L17-22 — admin bypasses). Models WITH the trait: AsabBrand, AsabRestaurant, Employee, Operation, Reminder, Asset, etc. Models WITHOUT it: **`AsabUser`** (uses only HasApiTokens/HasUuids/Notifiable/SoftDeletes, AsabUser L18) and legacy **`Branch`/`Supplier`/`Item`** (Branch.php L14-16). Consequences: `lookups/users` (L26 above), `lookups/branches` (L23), `lookups/suppliers` (L24), `lookups/items` (L25), and `search` users/branches/suppliers (L20) return rows from **all** companies for a non-admin caller. → task T01.3.

5. **§14.1 notification bell — unread counter, mark-all, mark-one all present?**
   Yes. `GET notifications` returns `meta.unreadCount` (NotificationController L30,43); `POST notifications/{id}/read` (L47-54) and `POST notifications/read-all` (L56-63) both user-scoped. Company copies mirror them (routes L776-778) with `PATCH .../read` + `mark-all-read` naming. Bell contract (title, body, createdAt→time-ago client-side, type, unread via `readAt==null`) is satisfied.

6. **§4.8 notification model — `icon` field present?**
   No. SRS §4.8/§14.1 list `icon` as a notification field, but `AsabNotification` has no `icon` column (`$fillable`: user_id,type,title,body,link,ref_type,ref_id,read_at — AsabNotification L14-16) and `index()` does not emit one. FE must derive the bell icon from `type`. → note in §6, minor task T01.5.

7. **§3 roles — do the shared T01 endpoints admit the right role set?**
   The shared block (L244) is `asab.tenant` only (any authenticated AsabUser with a tenant), which is correct for cross-cutting lookups/notifications/uploads/search/exceptions/prefs — all seven prototype roles need them. Company copies at L775/L804 explicitly enumerate `company-admin,head,accountant,branch,procurement`. `admin` (platform) has no company, so admin-prefixed copies exist at L209-211 (documented). `brand-owner`/`supplier` are mobile/hidden and not expected on these dashboard shared routes. Role catalogue (§3.1) is seeded in `AsabRolePermissionSeeder` (brand-owner L21). No blanket `authorize(){return true}` FormRequests exist in this scope (controllers validate inline; grep found none).

## 3. Gaps

- **NFR-2 / §3 zero-trust (auth/me, 2FA, data-export not asab-guarded)** → routes L95-110 accept any Sanctum token, not just AsabUser → a legacy-guard token can hit `auth/me`, `auth/2fa/setup`, `users/me/data-export`, provoking undefined behaviour on a non-AsabUser. Matters: identity-surface must fail closed, not on a missing relation.
- **NFR-3 tenant isolation (lookups/users, lookups/branches, lookups/suppliers, lookups/items, search)** → cross-company enumeration of user names/emails, branch names, supplier names for any non-admin. Matters: this is the foundation everyone else builds on; a leak here is systemic PDPL exposure.
- **Attachment ownership (attachments/{id} show/download/verify/delete)** → unscoped `findOrFail`, no company/owner check → any authenticated user reads or deletes any attachment (invoices, exports) by guessing/enumerating UUIDs. Matters: financial documents are the payload.
- **NFR-9 idempotency on shared mutations** → uploads, notification reads, 2FA, data-export, saved-filters are replay-unsafe on retry. Matters: FE retries (upload confirm, 2FA verify) can double-execute.
- **NFR-8 password-reset delivery** → `forgotPassword`/`resetPassword` write/consume a token row but no email is ever sent (no Notification). Matters: reset flow is non-functional end-to-end for real users.
- **SSO id_token signature unverified** → `SsoService::decodeIdToken` base64-decodes the JWT payload without verifying the IdP signature (JWKS deferred) → forged `email` claim = account takeover. Matters: it is a public login endpoint (routes L92).
- **Account-deletion request is inert** → no cancel endpoint and no job/command consumes `scheduled_for`; the "T+30 cancelable" contract is unfulfilled. Matters: PDPL erasure obligation not actually executed.
- **users/me/preferences not persisted** → PATCH echoes language/theme without storing → server-side sync claim is false. Matters: minor, but FE must know it is a client-only round-trip.
- **§4.8 notification `icon`** → no column/field; FE derives from `type`. Minor.
- **auth/logout leaves refresh token alive; refresh token is a full-ability PAT; sanctum expiration null** → session revocation and token-lifetime semantics are weaker than the `expiresIn:900` contract implies. Minor/hardening.

## 6. FE wiring notes

Module-specific items the FE doc MUST capture:

- **Response envelopes (critical):** these endpoints do NOT return `{success,message,data,meta}`. Single reads return the **bare** object; lists return `{data:[...],meta:{page,pageSize,total,totalPages}}` (list `meta` also carries `unreadCount` on notifications); mutations often return `204` with an empty body; errors return `{error:{code,message,messageAr,details},requestId}` with the HTTP status. FE error handling keys off `error.code` (e.g. `INVALID_CREDENTIALS`, `USER_INACTIVE`, `TWO_FACTOR_INVALID_CODE`, `RATE_LIMITED`, `EMAIL_MISMATCH`, `VALIDATION_ERROR`, `WRONG_ROLE`, `WRONG_TENANT`, `NOT_FOUND`).
- **Auth token model:** login → `{accessToken, refreshToken, expiresIn:900, user}`. `expiresIn` is advisory (server sanctum expiration is null). Send `Authorization: Bearer <accessToken>`. Refresh rotates both tokens; on 401 refresh, re-login. 2FA step-up: when login returns `{requires2fa:true, twoFactorToken}`, re-POST `auth/login` with `{twoFactorToken, code}` (no email/password).
- **`user` payload shape:** `{id,name,email,avatar,companyId,defaultPage,roles:[{key,scope,brandIds,restaurantIds,branchIds,moduleKeys}],permissions}` (permissions only on `auth/me`). `defaultPage` drives the post-login landing route (e.g. `brand-owner-dashboard`).
- **Module enum (`lookups/modules`) — Arabic labels verbatim:** `sales`=«المبيعات», `expenses`=«المصروفات», `purchases`=«المشتريات», `inventory`=«المخزون», `waste`=«الهدر», `assets`=«الأصول», `shifts`=«الورديات», `employees`=«الموظفين», `cash`=«النقدية». Each row carries both `key` and `value` (identical) plus `labelAr`/`labelEn`/`icon` — the distribution matrix reads `value`, gating reads `key`.
- **Exception-type enum (`lookups/exceptions`):** `cash_variance`=«فرق نقدي» (high), `missing_invoice`=«فاتورة مفقودة» (medium), `late_report`=«تقرير متأخر» (medium), `inventory_flag`=«تنبيه مخزون» (medium), `asset_unconfirmed`=«أصل غير مؤكد» (low), `shift_unclosed`=«وردية غير مُغلقة» (medium), `quota_warning`=«تحذير الحصة» (low).
- **CrossController static lookups (Arabic verbatim):** cities «الرياض/جدة/الدمام/مكة المكرمة/المدينة المنورة/الخبر/تبوك/بريدة/أبها/الطائف/الأحساء/حائل»; units «كجم/لتر/قطعة/كرتون/كيس/عبوة/شريحة»; asset-categories «معدات مطبخ/أثاث/أجهزة إلكترونية/مركبات/أخرى» (with `depreciationRate`); expense-categories «إيجار/خدمات (كهرباء/ماء)/رواتب/تسويق/صيانة/أخرى»; supplier-categories «مواد غذائية/مشروبات/تغليف/معدات/خدمات».
- **Notification bell (§14.1):** poll `GET notifications?unreadOnly=…&type=…&page=&pageSize=`, read the counter from `meta.unreadCount`; `readAt==null` = unread dot; there is **no `icon` field** — derive the bell icon from `type`; compute time-ago client-side from `createdAt` (ISO-8601, Asia/Riyadh). Mark-one = `POST notifications/{id}/read` (company surface uses `PATCH`); mark-all = `POST notifications/read-all` (company: `POST notifications/mark-all-read`).
- **Doc-conformance aliases — canonical paths:** notifications live at the shared `/notifications*` (canonical) with company copies under `/company/me/notifications*`; the admin SPA additionally reaches `notifications/preferences` and `lookups/modules` under `/admin/*` (same handlers). For a platform admin (no companyId) use the `/admin/*` copies; for company roles use `/company/me/*` or the shared copies. FE should call the surface matching the logged-in role's dashboard.
- **Idempotency:** until T01.2 ships, do NOT rely on `Idempotency-Key` for uploads/2FA/data-export/saved-filters (header is currently ignored on the shared group). Admin/company mutation surfaces already honor it.
- **Uploads flow:** either (a) `POST uploads/presigned-url` → `POST uploads/direct` (multipart `file`) → `POST uploads/{attachmentId}/confirm`, or (b) `POST uploads/direct` directly. Attachment payload is camelCase (`ownerType,ownerId,filename,mimeType,size,storageKey,publicUrl,label,verifiedAt,uploadedAt`). Max 10 MB.
- **Known-unstable endpoints (flag as "pending fix"):** `lookups/users|branches|suppliers|items`, `search`, `attachments/{id}` reads/writes, `users/me/preferences` (client-only echo), `auth/forgot-password` email delivery, `auth/sso/*/callback` (OIDC only, unverified sig). List these in the FE doc so the team doesn't integrate against leaking/no-op behaviour before the tasks land.
