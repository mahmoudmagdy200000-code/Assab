## 2. Answers to critical checks

1. **Does upload/{reportType} create pipeline operations with attachments?** Half. Platform `POST /branch/upload/{reportType}` (BranchDashboardController.php:53–82) creates a real pending pipeline Operation — `OperationFactory::createFromUpload` (Modules/Admin/app/Services/OperationFactory.php:26–67) writes `status='pending'`, an ApprovalStep `stage_id='submit'` («أُنشئ السجل: …»), fires realtime `operationCreated` and notifies the accountant role («سجل جديد بانتظار المراجعة»). But it persists **no attachments** and applies **no validation** (`$request->all()` into payload, L64). The company-surface `POST /company/me/branch/upload` DOES persist multipart `attachments[]` (Attachment rows on public disk, linked to the op, `attachment_count` synced — BranchCompanyController.php:109, 131–173), plus a `sign-attachment` presign route (routes:692). Canonical BRM-2 path = company surface.
2. **Items count modal → submits a daily count operation?** Yes. `POST /company/me/branch/items/count` (BranchCompanyController.php:175–187) validates `counts[]` and calls `OperationFactory::createFromUpload('inventory', {counts, countType:'daily'}, …)` → pending Operation in the accountant pipeline (SRS BRM-4.2 "submit to accountant"). Caveats: item ids are not validated against the branch's configured `BranchInventoryList`, and expected qty is neither returned by GET items (BranchDashboardController.php:154–183) nor stored alongside the count.
3. **Overview returns tasks-of-day states (مكتمل/معلق/لاحقاً)?** No. `overview` returns `requiredReports[]` with boolean `uploadedToday` and `lastStatus` `'success'|'missing'` only (BranchDashboardController.php:336–360). There is no tri-state مكتمل/معلق/لاحقاً enum, and the fourth BRM-1.2 task (close evening shift) is absent from the checklist.
4. **Crew/attendance data source?** None exists. No attendance table/model/route in Modules/Admin (grep `طاقم|attendance` returns nothing). The only adjacent data: `asab_employees.shift_type` and active shifts (`asab_shifts` has supervisor only, no crew members). BRM-1.3 requires name/role/shift/attendance-status — a data source must be created or derived (e.g., employees on today's shift_type + legacy cashier attendance bridge).

## 3. Gaps

- **BRM-1.1/1.2 → overview is a thin stub of the SRS screen** — no monthly hero (target vs actual %; `branches.asab_monthly_target` already exists and is used by CompanyDashboardService.php:23–39, just not here), no month sales/expenses/net profit, no tri-state task list, no close-evening-shift task. Why: the main branch-manager landing screen can't be built by FE.
- **BRM-1.3 → «طاقم اليوم» has no backend at all.** Why: overview crew card is a hard SRS requirement; needs a data-source decision (derive from employees.shift_type vs legacy cashier shifts bridge).
- **BRM-2.1 → platform upload/{reportType} drops attachments and validates nothing.** Why: unvalidated `$request->all()` into payload is a data-quality and abuse risk; the sales form requires attachment support on whichever path FE uses. (Company-surface upload already does this right — either close the platform gap or mark the company path canonical and thin the platform one.)
- **BRM-3.2/BRM-4.1/BRM-4.2 → items endpoint has no price/code/min-level/expected-qty/stock-status (كافٍ/منخفض/حرج).** Why: the أصناف table and the «تسجيل جرد» modal both need these; columns for min level/expected qty don't exist yet (`asab_inventory_catalog` has only unit_price; `asab_branch_inventory_lists` has only is_flagged).
- **BRM-3.3 → request-new supplier is fire-and-forget** (notification only, HTTP 202, nothing stored). Why: chips «قيد المراجعة»/«معتمد» can't be rendered, procurement can't list pending requests, requests are lossable.
- **BRM-5.1 → openShift silently discards `cashierEmpNumber`** (no column on `asab_shifts`). Why: the SRS open-shift form's cashier select does nothing; accountant board can't show who ran the shift. **Fix owned by T08.2 — not tasked here.**
- **BRM-7 → SRS says name/manager/phone editable; code allows only manager** (BranchDashboardController.php:246–295 makes branchName/phone read-only, citing a later client requirement). Why it matters: SRS↔code contradiction must be resolved and documented before FE builds the settings form, else fields will 422/no-op.
- **BRM-3.1 → employees list: no pagination, no search.** Why: violates the memory-cap rule and the SRS table has a search box.
- **§5.2b → dashboard uploads stamped `origin='mobile'`** (OperationFactory.php:38). Why: origin chip (مصدر العملية) on accountant screens will lie for dashboard-submitted ops; purchaseRequests listing depends on this value (brittle).

## 6. FE wiring notes

- **Canonical paths:** company surface `/api/v1/company/me/branch/*` is canonical for all mutations (it carries idempotency + audit middleware); platform `/branch/*` is the read/legacy alias. Settings: **PUT** is canonical on the company surface, PATCH is a doc-conformance alias (routes/api.php:709–711); on the platform surface only PATCH exists.
- **Upload:** use `POST /company/me/branch/upload` with the flat body `{reportType, date, salesHalalas|expensesHalalas, shift, expenseNote}` + multipart `attachments[]` (≤10MB/file); response is a superset `{operations:[…], uploadId, reportType, status:'success', createdOperationId, uploadedAt, attachments:[…]}`. `sign-attachment` returns a local direct-upload URL (`/api/v1/uploads/direct`), not S3.
- **Money is integer halalas everywhere** (`salaryHalalas`, `salesHalalas`, `openingCashHalalas`, `cashLimitHalalas`).
- Enums with Arabic labels the FE must render: report names (تقرير المبيعات / جرد المخزون اليومي / تقرير النقدية / تقرير الهدر / المشتريات / المصروفات); tasks-of-day states `completed مكتمل / pending معلق / later لاحقاً` (after T12.1); urgency `normal عادي / urgent عاجل⚡`; stock status `ok كافٍ / low منخفض / critical حرج` (after T12.4); supplier chips `approved معتمد / pending_review قيد المراجعة` (after T12.6); shift values صباحي/مسائي/كامل اليوم.
- Doc-conformance request aliases already live: employees `salaryHalalas`→monthly_salary, `shift`→shiftType; purchase-requests `itemName`→item, `priority`→urgency; shifts/open `cashierId`→cashierEmpNumber, `registerOpeningHalalas`→openingCashHalalas; shifts/close `cashInDrawerHalalas`/`salesSystemHalalas`. FE should send the canonical (first-listed doc) names.
- Settings GET returns `readOnlyFields: ['branchName','phone','address']` and `shiftConfig.readOnly:true` — FE must render those disabled; sending them is silently ignored (no 422).
- Error shapes: 409 `SHIFT_ALREADY_OPEN` («يوجد وردية مفتوحة بالفعل لهذا الفرع»); 400 `INVALID_INPUT` («نوع تقرير غير معروف») on unknown reportType.
- Screen mapping: overview → «نظرة عامة» (hero/KPIs/مهام اليوم/طاقم اليوم); upload → «رفع البيانات» forms + success screen; employees → «الموظفون» table+add modal; items(+count) → «الأصناف» + «تسجيل جرد» modal; suppliers(+request-new) → «الموردون» + «طلب مورد جديد»; purchase-requests → hidden «طلبات الشراء»; shifts → hidden «شفتات الفرع»; settings → «إعدادات الفرع».
