## 2. Answers to critical checks

1. **Feature flag default value:** `false` — `config/features.php:18`: `'asab_supplier_portal' => (bool) env('FEATURE_ASAB_SUPPLIER_PORTAL', false)`. When off, the route group's closure early-returns before registering any route (routes/api.php:457–459), so all `/asab/supplier/*` paths 404. No .env.example entry exists for the flag (grep found only config/features.php). Legacy mobile `/api/v1/supplier/*` (Modules/Supplier, own guard) is unaffected, and the `supplier` role is seeded (AsabRolePermissionSeeder.php:20; demo user supplier@asab.sa in AsabDemoSeeder.php:90).
2. **Orders show 'from' (procurement vs branch)?** No. `present()` returns only `{id, publicId, total, status}` (SupplierController.php:256–259). The data to derive it exists: ops carry `branch_id`, branch-originated requests have `payload.kind='branch_request'` (BranchCompanyController.php:220), and procurement's consolidate/send stamps `payload.supplierId` (ProcurementController.php:150–160, PurchaseOrderGroup supplier_id) — so `from` = branch name when kind=branch_request, else «مدير المشتريات». Not implemented → gap SUP-1.1.
3. **Separate approved/rejected lists supported by filters?** Yes, mechanically: `GET orders?status=accepted` / `?status=rejected` works because accept()/reject() write exactly those status values, and pagination is per-status (SupplierController.php:50–54). Export mirrors it with a broader accepted-synonym whereIn (ExportService.php:563–567). BUT the list endpoint's filter is an exact match only — procurement-side statuses (`approved`, `confirmed`) that ExportService treats as accepted will NOT appear under `?status=accepted` in the JSON list, and the overview KPI uses `approved` (the value accept() never writes). The status vocabulary must be unified (see T13.1/T13.2).

## 3. Gaps

- **SUP-1.4 / overview KPI bug → `acceptedThisMonth` filters `status='approved'` while accept() writes `'accepted'`** (SupplierController.php:35 vs 70). Why: the KPI is permanently 0 — a demo-visible correctness bug; also year-agnostic `whereMonth` and totalSales including pending/rejected inflate numbers; trend missing.
- **SUP-1.1 → orders rows missing `from` (procurement OR branch), items text, orderDate, deliveryDate.** Why: the «الطلبات الواردة» table cannot render its columns; FE has nothing to show but a total.
- **SUP-1.2 → no status-machine guards on accept/reject/mark-delivered.** Why: a supplier can flip a delivered order back to rejected or deliver a pending one — corrupts procurement's pipeline view; SRS defines a strict `pending → confirmed → delivered | rejected` machine.
- **Status vocabulary drift → code `accepted` vs SRS key `confirmed` (مقبول), and procurement surfaces use `approved`.** Why: list filter is exact-match, so the same logical state is split across three strings; FE separate-lists filter will silently miss rows.
- **SUP-2.1 → item `code` not updatable via PATCH.** Why: CRUD contract incomplete; suppliers can't fix a typo'd code without delete+recreate.
- **SUP-3 → reports route returns hardcoded empty `topItems/topBranches/monthly`.** Why: violates the dead-code rule (route exists but is partly non-functional); SUP-3 is DEFERRED so the cheap fix is to remove/flag the stub keys, not build them.
- **No Pest coverage at all for `/asab/supplier/*`** (no supplier test file exists in tests/Feature). Why: flag-gated code rots invisibly; the accepted/approved bug proves it.

## 6. FE wiring notes

- **Hidden v1:** entire section behind `FEATURE_ASAB_SUPPLIER_PORTAL` (default off) — endpoints 404 when disabled; FE must feature-flag the whole supplier area, not per-screen. Namespace is `/api/v1/asab/supplier/*` — do NOT use `/api/v1/supplier/*` (that's the legacy mobile portal with a different guard).
- Order status enum (key + Arabic label): `pending في انتظار الرد` · `accepted مقبول` (SRS calls this state «confirmed» — backend key is `accepted`) · `delivered تم التسليم` · `rejected مرفوض`. Separate lists = `GET orders?status=accepted|rejected|pending` (paginated per list, `page`/`pageSize`≤100).
- Item fields: `price` and `priceHalalas` are the same integer-halalas value (send `priceHalalas`, read either); `available` boolean mirrors `status` `active نشط / inactive موقوف`; `minQty` = أقل كمية للطلب. Toggle endpoint needs no body.
- Reject requires `reason` (string ≤500) — FE must not submit without it. Accept optionally takes `deliveryDate` + `note`.
- Exports: `GET orders/export?status=accepted|rejected&format=xlsx|csv` and `GET items/export?format=…` return binary files (not the JSON envelope) with Arabic headings.
- KPI card mapping (SUP-1.4): `newOrders` → «طلبات جديدة», `acceptedThisMonth` → «مقبولة هذا الشهر», `totalSalesThisMonth` (+trend after T13.2) → «إجمالي مبيعاتي», `activeItems`/`totalItems` → «أصناف نشطة n/m». Screen mapping: overview → لوحة المورد; orders → «الطلبات الواردة» + قبول/رفض actions + تم التسليم; items → «أصنافي» CRUD + toggle; reports → deferred (SUP-3).
- Ownership: everything is implicitly scoped to the logged-in supplier user (`asab_suppliers.user_id` / `supplier_user_id`) — FE never sends a supplier id.
