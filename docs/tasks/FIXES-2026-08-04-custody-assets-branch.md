# إصلاحات 2026-08-04 — تحويل العهدة / الأصول الثابتة / بيانات فرع جديد

ثلاث ملاحظات من الاختبار الميداني، وكلها كانت أخطاء حقيقية في الباك-إند.

## 1) تحويل مبلغ من صاحب المطعم إلى مدير الفرع: لا إشعار، ولا استلام، والرصيد 0.00

**السبب:** نموذج الدفع (`POST /api/brand-owner/payment-form`) كان يُنشئ صفًّا في
`custody_requests` بحالة `Pending` وينتهي عند ذلك:

- لا إشعار لأي طرف — دورة حياة طلب العهدة كلها (إنشاء / موافقة / رفض) كانت بلا إشعارات، رغم وجود نصوصها الجاهزة في `Modules/Notification/resources/lang`.
- لا خطوة استلام للمدير — `CustodyTransactionService::createTransactionFromRequest()` كانت **دالة ميتة لا يستدعيها أحد**، فلا تُكتب أي حركة `custody_transactions`، ولذلك ظلّ «رصيد عهدة الفرع» = 0.00 مهما بلغت الطلبات.
- التسمية «Me (Branch Manager)» كانت ثابتة في الكود، فظهر تحويل المالك وكأن المدير هو من طلبه.

**ما تم:**

| العنصر | التغيير |
| --- | --- |
| `CustodyNotifier` (جديد) | إشعار لكل مرحلة: تحويل من المالك ← المدير، طلب من المدير ← المالك، موافقة/رفض ← المدير، تأكيد الاستلام ← المالك. الإرسال best-effort ولا يُرجع أي حركة مالية. |
| `POST /api/custody/requests/{id}/confirm-receipt` (جديد) | **مدير الفرع فقط.** يكتب حركة `custody_transactions` داخلة (cash-in) ويضبط الحالة `Completed` + `received_at`. هذه هي الخطوة الوحيدة التي تُحرّك رصيد عهدة الفرع. |
| ترحيل قاعدة البيانات | `custody_requests.received_at` + `received_by`، وتحويل `custody_request_timeline.stage/status` من enum إلى string (مرحلة «Receive Case» كانت مرفوضة بقيد CHECK). |
| التسميات | `submittedBy` يتبع مُنشئ الصف فعلًا: «اسم المالك (Brand Owner)» أو «Me (Branch Manager)»، و`type` = `Owner Transfer` للتحويلات. |
| الرصيد | «الرصيد الحالي» في شاشة رصيد عهدة الفرع لم يعد يتأثر بفلتر الفترة (كان فلتر «آخر 7 أيام» يعرض جزءًا من الرصيد الحقيقي). |

**عقد الواجهة الأمامية:**

```jsonc
// GET /api/custody/requests  و  GET /api/branch-manager/ledger/branch-custody-balance
{
  "id": "…",
  "type": "Owner Transfer",             // أو "Custody Request"
  "submittedBy": "صاحب المطعم (Brand Owner)",
  "status": "pending",                   // pending | approved | rejected | completed
  "amount": 5000,
  "canConfirmReceipt": true,             // ← أظهر زر «استلام» عند true
  "receivedAt": null
}
```

```jsonc
// POST /api/custody/requests/{requestId}/confirm-receipt   (بدون body)
{ "success": true, "data": { "requestId": "…", "status": "completed", "receivedAt": "2026-08-04T…" } }
// 422 إذا لم يكن الطلب بانتظار الاستلام أو سبق استلامه، 403 لغير مدير الفرع
```

**القاعدة:** تحويل المالك يُستلم مباشرة (الدافع تصرّف بالفعل)؛ طلب المدير لا يصبح قابلًا
للاستلام إلا بعد موافقة المالك. الاستلام مرة واحدة فقط — لا يمكن تكرار إضافة الرصيد.

## 2) الأصول الثابتة المرفوعة من الداشبورد لا تظهر للفرع

**السبب — عيبان:**

1. المستورد الجماعي (`upload/fixed-assets`) كان يكتب في `asab_assets` **دون إطلاق**
   `AssetAssignedToBranch`. المسارات الفردية (`AssetController`, `AssetDraftService`) تُطلقه،
   وهو الذي يُنشئ `fixed_asset_pending_receipts` ويرسل الإشعار. فبقيت شاشة «طلبات الاستلام»
   فارغة هيكليًا، وشاشة أصول الفرع تقرأ 0 — لأن سجل الجوال (`fixed_assets`) لا يُملأ إلا بعد
   تأكيد الاستلام.
2. الرفع على مستوى البراند كان يُهمل عمود «اسم الفرع» الموجود في القالب العربي أصلًا، فتهبط
   كل الصفوف بـ `branch_id = NULL` — أي خارج أي فرع.

**ما تم:**

- المستورد يُطلق `AssetAssignedToBranch` بعد الـ commit لكل أصل `pending_branch` له فرع → طلب استلام + إشعار لمدير الفرع.
- «اسم الفرع» يُقرأ الآن ويُطابَق على فروع البراند المرفوع عليه (لا يتخطّى البراند أبدًا؛ الاسم المكرر داخل البراند يُترك بلا فرع بدل التخمين؛ الاسم غير المعروف لا يُفشل الصف).
- إصلاح البيانات القائمة في الإنتاج:

```bash
php artisan asab:bridge-backfill --dry-run   # يعرض الأصول المعلّقة بلا طلب استلام
php artisan asab:bridge-backfill             # يُنشئها فعليًا (idempotent: مفتاحها asab_asset_id)
```

بعد التشغيل تظهر أصول «الريان 1» في «طلبات الاستلام» على الجوال؛ وبتأكيد المدير للاستلام
تُنشأ صفوف `fixed_assets` وتبدأ عدادات شاشة الأصول (ممتاز / صيانة / مشكلة) بالعمل.

## 3) فرع جديد وفيه بيانات قديمة من تاريخ سابق

**السبب:** إسناد المدير من الداشبورد كان يكتب `branches.asab_manager_user_id` ونطاق الدور في
ASAB فقط. التطبيق يعتمد كليًّا على `branch_managers.branch_id` — وهذا العمود لم يكن يُكتب إلا
مرة واحدة عند إنشاء الحساب. فالمدير الذي يُنقل (أو يُسند لفرع جديد) يظل هاتفه يفتح **فرعه
السابق**: جرد قديم بتواريخ سابقة، تقارير هدر قديمة، وسجل أصول فرع آخر.

**ما تم:**

- `ManagerBranchSyncService` (جديد) يُعيد توجيه حساب الجوال عبر خريطة الهوية، ويُستدعى من كل مسار إسناد: إنشاء فرع، تعديل فرع، تعديل مستخدم دوره `branch`، ونقل المدير من بوابة الشركة.
- فلترة العهدة أصبحت بالفرع لا بالمدير فقط: `GET /api/custody/requests` و`GET /api/custody/transactions` ورصيد المصروفات المتاح — فلا تتبع بيانات الفرع السابق المديرَ إلى فرعه الجديد.
- إصلاح الحالات القائمة:

```bash
php artisan asab:sync-manager-branches --dry-run   # جدول: المدير / الفرع في الجوال / الفرع في الداشبورد
php artisan asab:sync-manager-branches             # يُنفّذ التصحيح (المرجع هو الداشبورد)
```

**ملاحظة إضافية مكتشفة أثناء الإصلاح:** `POST /api/v1/admin/restaurants/{id}/branches` كان
يفشل دائمًا بخطأ قيد `branches.location` (NOT NULL ولم يكن يُكتب). تم ضبطه من العنوان أو
المدينة أو اسم الفرع.

**تنبيه تشغيلي:** بيانات الفرع القديم تبقى على الفرع القديم — هذا هو السلوك الصحيح. إن كان
الفرع الجديد يحتاج جردًا/أصولًا فيجب إنشاؤها له، لا نقلها.
