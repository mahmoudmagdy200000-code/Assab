## 2. Answers to critical checks

1. **Day-completeness endpoint — NO, missing entirely.** No route in `Modules/Admin/routes/api.php` and no service computes «n عملية مطلوبة — m مكتملة · k ناقصة». Repo grep for `مكتملة`, `ناقصة`, `completeness`, `dayPills`, `expectedOps` under `Modules/Admin` returns zero code hits. There is also no data model for "expected submissions per branch per day" (the `asab_reminders` table has `days_missing`/`required_by` but rows are seeded, not derived). Must be built (T04.3).
2. **Full channel enum in sales payload — NO.** The §4.3 enum (كاشير (POS) 🖥️ · نقدي (صندوق) 💵 · بنكي / بنك الرياض (مدى) 🏦 · طلبات 🔴 · هنقرستيشن 🟠 · جاهز 🟡 · تو يو (ToYou) 🔵 · نينجا ⚫) appears **nowhere in code** — grep for `هنقرستيشن|نينجا|تو يو|كاشير` across `Modules/Admin/app` → zero hits. Reality: reconciliation accepts only `cashAmount/cashHalalas`, `bankAmount/bankHalalas`, and free-text `deliveryApps[].name` (AccountantController.php:143–155); `ReportService::salesByChannel` reads coarse `cash/bank/delivery` keys with labels «نقدي / شبكة/بنك / تطبيقات التوصيل» (ReportService.php:96–130); the branch upload captures **only totals** (`sales.totalHalalas` / `salesHalalas`, BranchCompanyController.php:61–67, 86–106), so per-channel expected amounts never exist. `GET /operations/{id}` merely echoes whatever payload was stored — for all seeded sales ops that is no channels at all (AsabOperationSeeder.php:29–33).
3. **Variance allocation validates full allocation + posts `asab_employee_movements` atomically — PARTIAL.** Atomicity ✅: `SalesVarianceService::assign` wraps all `EmployeeMovement::create` rows (table `asab_employee_movements`, EmployeeMovement.php:12) plus the payload write in one `DB::transaction` (SalesVarianceService.php:40–71), employee resolved tenant+branch-safe (lines 82–97), route protected by `asab.idempotency`. Full-allocation guard ❌ **broken for the SRS case**: the check `if ($variance > 0 && $sum !== $variance)` (line 29) reads `payload['varianceHalalas']`, which the reconciliation endpoint stores as `collected − expected` (AccountantController.php:171) — a **shortfall is negative**, so the guard never fires and any partial/over allocation is accepted; when the payload lacks a variance the sum is simply trusted. Additional holes: no 409 guard on `final-approved` operations (locked ops can receive movements); movements carry no `category` («فرق مبيعات») — description is hardcoded «تحميل فرق كاش — {ref}» and the table has no category column (migration `2026_06_05_000001_create_asab_ops_detail_tables.php:77–88`).
4. **Locked branch-total rule — YES, enforced server-side (with caveats).** The PATCH validation whitelist contains no total field; the expected total is derived from the immutable `op->amount` (fallback payload keys) and only cash/bank/delivery-app entries are writable (AccountantController.php:143–171). Edits on `final-approved` ops are refused with 409 `OP_ALREADY_FINAL` (lines 140–142) — matches «مقفل» + «hidden once final-approved». `sales-lines/{rowId}` likewise never touches `op->amount` (lines 193–238). Caveats: `op.match`/`diff_note` are not recomputed after edits (G7) and `sales-lines` rows are not cross-validated against the locked total.
5. **Dashboard KPIs match ACC-0.2 + module grid — NO, both variants drift.** Company surface (`AccountantCompanyController@dashboard`, lines 27–49): has `awaitingReview` (pending-for-me ✅ scoped), `iApproved` by `approved_by_id` ✅, but **no «new ops today» KPI** and **`approvalRatePct` is hardcoded `100`** (line 42); module grid is `pendingByModule` — a sparse pending-only group-by with **no totals and no urgent flag** (ACC-0.3 wants pending/total + urgent red dot over the nine modules). Legacy surface (`AccountantController@dashboard`, lines 52–76): computes a real `approvalRate` and grid with pending+total ✅ but `iApproved` counts `status='approved'` (not actor-attributed), still no new-today KPI, grid covers only 6 of 9 modules (missing shifts/assets/employees, lines 323–338) and no urgent dot. Neither returns ACC-0.6 progress bars nor the ACC-0.1 scope subtitle (derivable from `GET /auth/me` `roles[].branchIds/moduleKeys`, AuthService.php:119–146).

## 3. Gaps

- **G1 · ACC-1.2** → No day-completeness endpoint or expected-per-day model → the day pills (الكل/اليوم/أمس/قبل يومين/الأسبوع الماضي) and the banner «n عملية مطلوبة — m مكتملة · k ناقصة» have no data source; accountants cannot see which branches are missing today's sales statement — the module's core "what's missing" signal.
- **G2 · §4.3 / ACC-1.4** → No sales channel enum; payload is coarse `cash/bank/deliveryApps(free text)`; branch upload captures totals only → the per-channel reconciliation table (entered vs expected vs diff vs status, grand-total row) cannot render; delivery-app names will fragment («هنقرستيشن» vs "Hunger Station"), breaking P&L channel rollups downstream (RPT/HEAD).
- **G3 · ACC-1.4 shortfall allocation** → Full-allocation rule bypassed for negative (shortfall) variance — the exact SRS case «الفرق يُخصم من حساب المسؤول»; partial allocations post silently, so employee ledgers under-collect the gap; also no 409 on final-approved ops (locked records can gain movements) and no «فرق مبيعات» category on movements (ACC-7.4 sources become indistinguishable).
- **G4 · ACC-0.2/0.3** → Company dashboard `approvalRatePct` hardcoded 100 (a lie in production), no new-today KPI, module grid lacks totals/urgent/nine-modules; legacy `iApproved` not actor-attributed → the four headline KPIs the accountant lands on are wrong or absent.
- **G5 · ACC-0.6** → No «تقدم اليوم» progress bars (review/approval/documentation/completed-branches) → dashboard section has no endpoint.
- **G6 · ACC-1.1/1.3/1.5** → No sales-KPIs endpoint (total sales today + branch count + trend, total collected, total variance + case count, zero-variance branches) and list rows omit per-channel/collected/variance columns → matching table and variance alert banner cannot be built from `GET /operations?moduleKey=sales` alone.
- **G7 · §5.3 / ACC-1.3** → `op.match`/`diff_note` never recomputed after `sales-details`/`sales-lines` edits → a reconciled operation keeps its stale ⚠ diff badge (or worse, keeps ✓ after edits introduce a variance); «✓ مطابق» column and needs-attention widget become untrustworthy.
- **G8 · ACC-1.4 attachments** → Files are persisted and linked (`asab_attachments.owner_id = op.id`) but no endpoint lists an operation's attachments → POS report PDF / bank statement / aggregator report panel has no data source for sales ops.
- **G9 · zero-trust** → Single-op export (`ExportService::operation`, line 182) and bulk export (line 412) skip assigned-branch scoping (tenant scope only) → a branch-scoped accountant can export other branches' operations in the same company (bulk half is T03.7; single-op fix owned here, T04.9).
- **G10 · §5.4 / ACC-0.5** → Reject reasons free-text (no fixed list, no sales-specific adds) and «طلب توضيح» endpoint absent — **owned by T03.4/T03.5**; T04 must verify they surface for the accountant role and document them.

## 6. FE wiring notes

- **Canonical vs aliases** (FE must use canonical; aliases documented as deprecated): `PATCH /company/me/operations/{id}/sales-details` is canonical — `PATCH …/reconciliation` (routes/api.php:629) is a doc-conformance alias; `POST …/sales-variance/assign` is canonical — `POST …/variance-allocations` (:630) is the alias (its response adds `remainingVarianceHalalas`); legacy `PATCH /accountant/operations/{id}/reconciliation` (:345) is the same handler for the internal-dashboard surface.
- **Two surfaces**: company portal accountant screens use `/v1/company/me/*` (role `accountant`, headers: tenant context + `Idempotency-Key` on mutations — group middleware `asab.tenant, asab.idempotency, asab.audit`); the internal dashboard uses `/v1/accountant/*` (role `accountant|head`). **`GET /operations/{id}`, `GET /operations/{id}/audit-trail`, and `POST /operations/{id}/reject` exist only at the shared `/v1/operations/*` paths** — there are no `/company/me` variants; FE calls them directly (they are tenant-scoped and accountant-allowed).
- **IDs**: every `{id}` accepts either the uuid or the `public_id` (e.g. `OPS-2401`).
- **Money**: all amounts are integer **halalas** (`…Halalas` keys). `sales-details` accepts legacy `cashAmount/bankAmount` and doc aliases `cashHalalas/bankHalalas` — send the `…Halalas` form.
- **Enums (verbatim Arabic)**: status `pending قيد المراجعة / approved تمت الموافقة «معتمد - مرحلة 1» / rejected مرفوض / final-approved معتمد نهائياً 🔒`; match `exact متطابق ✓ / review يحتاج مراجعة / diff فرق ⛔`; sales channels (after T04.1) `pos كاشير (POS) 🖥️ · cash نقدي (صندوق) 💵 · bank بنكي / بنك الرياض (مدى) 🏦 · talabat طلبات 🔴 · hungerstation هنقرستيشن 🟠 · jahez جاهز 🟡 · toyou تو يو (ToYou) 🔵 · ninja نينجا ⚫`; rejection reasons: generic 7 + sales adds «تقرير POS مفقود، كشف البنك غير مرفق» (from T03.4 lookup); movement category `sales_variance فرق مبيعات`. Until T03.1 lands, list rows return **raw keys only** — FE must not hardcode label maps long-term.
- **ACC-0.1 scope subtitle**: compose from `GET /v1/auth/me` → `roles[].branchIds` + `roles[].moduleKeys` (AuthService `userPayload`); dashboard adds a `scope` block after T04.5.
- **Pagination/filter contract**: `page`, `pageSize` (cap 100); list meta contains `summary` counts; filters `moduleKey`, `status`, `branchId`, `match` accept comma-separated lists; `search` matches `public_id`; `dateFrom/dateTo` arrive with T03.3/T04.10. Branch names are NOT embedded in op rows — resolve via `GET /v1/lookups/branches` once per session.
- **Screen mapping**: dashboard «ملخص اليوم» → `GET /company/me/accountant/dashboard` (+ `GET /users/me/quick-stats` header widget, `GET /accountant/dashboard/activity-heatmap` heatmap card); sales list «المبيعات» → `GET /company/me/operations?moduleKey=sales` + `GET /company/me/sales/kpis` + `GET /company/me/sales/day-completeness` (day pills) + `GET /company/me/operations/export?moduleKey=sales`; detail screen → `GET /operations/{id}` (payload + accountantNotes + varianceAllocations) + `GET /operations/{id}/audit-trail` (timeline) + `PATCH sales-details` (edit mode «تعديل الأرقام»/«💾 حفظ») + `POST sales-variance/assign` (allocation modal, quick-fill «⚡ المتبقي» = `remainingVarianceHalalas`) + `GET /company/me/branches/{branchId}/employees/lookup?empNumber=` (name auto-fill) + `POST …/notes` + attachments panel (`GET /operations/{id}/attachments` after T04.8); approve → `POST /company/me/operations/{id}/approve`; reject modal → `POST /operations/{id}/reject` `{reason, notes?}`; bulk «اعتماد المحدد (n)» → `POST /company/me/operations/bulk-approve` `{operationIds[]}` → render per-id `failed[]` codes.
