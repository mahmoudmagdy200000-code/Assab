## 2. Answers to critical checks

1. **Pending grouped by accountant×module with group totals + فروق badge?** **No — flat list only.** `HeadController::listByStatus` (HeadController.php L233–254) returns a paginated flat array; each row carries `accountantId/accountantName/moduleKey/match` (L292–318) so the FE *could* group a single page client-side, but there is no server grouping, no per-group totals, and no per-group «⚠ يوجد فروق» flag. Grade 🟡 on #2, ❌ as a grouped endpoint (#33).
2. **Group-level bulk approve + return-for-review?** **Both missing.** Bulk: `POST /operations/bulk-approve` exists (routes L250) but `OperationService::bulkApprove` (L160–180) delegates to `approve()` which `assertStatus(pending)` (L23–25) — every approved-status op in the head queue fails with `OP_NOT_PENDING`, so heads cannot bulk-final-approve. Return-for-review: no route, no service method, no Arabic string «إرجاع للمراجعة» anywhere in `Modules/Admin` (grep verified). `correction` is a different flow (new linked op).
3. **Performance returns rate/rating/approved/pending per accountant?** **Yes.** `HeadMetricsService::accountantsPerformance` (L98–171): `rate`/`approvalRatePct`, `rating` = min(5, rate/20), `approved`, `pending` (branch-assignment-scoped), plus `branches`, `avgTime`, `prevRate`, `level`+`levelLabelAr` («ممتاز/جيد/مقبول/يحتاج تحسين»)+`levelCls`, and `recentMovements`. Served on both surfaces (routes L322, L603). ✅
4. **ERP batch auto-creation on final-approve vs manual `erpCreateBatch` — which is it?** **Manual only.** `OperationService::finalApprove` (L84–114) never touches `ErpBatchService`; batches exist only when a head calls `POST /erp/batches` (routes L260) or per-op `POST /company/me/operations/{id}/post-to-erp` (L608). The SRS model (ERP-1 batches in `ready` status per day+module, Epic-2 "auto-batch on final approval") is not implemented — there is no `ready` stage at all: creation == posting.
5. **Failed batch retry endpoint?** **No.** No retry route in routes/api.php; `ErpBatchService::create` sets `status => 'success'` unconditionally (L40, "synchronous mock post"), so `failed` can never occur and the SRS `ready|exported|failed` enum is unrepresented (migration default `'queued'` is dead too — 2026_06_02_000001 L342).
6. **Direct API post (ترحيل API) vs file download — both?** **Both exist, with defects.** API post: `POST /erp/batches` (filters or ids — the ERP-3 «ترحيل API» bulk form) + single-op `post-to-erp` — both stamp `erp_posted` and write a م5 step. Downloads: batch `download.json`/`download.csv` work; `download.xlsx` returns CSV bytes with a `.csv` filename (ErpController L47–50); the filtered «تصدير Excel» is `GET /operations/export` (ExportService, real spreadsheet, full filters) ✅.
7. **Rollup interaction: batches per day+module with `EXP-YYYY-MM-DD-nnn`?** **No.** `ErpBatchService::create` produces ONE batch for the whole selection regardless of day/module, numbered `'ERP-BATCH-'.now()->format('Ymd').'-nnn'` = `ERP-BATCH-YYYYMMDD-nnn` (L32) — matches neither SRS format (`EXP-YYYY-MM-DD-nnn` nor `ERP-BATCH-YYYYMM-nnn`). The §5.2c rollup interaction *does* work at flag level: `erp_posted` is stamped per op, so `ready_erp → exported` derivation has its input.

Tenant-scope note: `Operation` carries the `BelongsToTenant` global scope (Operation.php L17), so all HeadController/HeadMetricsService operation queries are company-isolated for non-admin heads. `ErpBatch` does **not** (ErpBatch.php — no scope, no company filter in `erpBatches`/`ErpController`), which is the one real isolation hole in this module.
