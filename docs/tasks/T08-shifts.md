## 2. Answers to critical checks
1. **Late status derivation — NO.** `'late'` exists only as a migration comment (`Modules/Admin/database/migrations/2026_06_05_000001_create_asab_ops_detail_tables.php:56` — `active|late|closed`) and in read queries (`Accountant/ShiftController.php:20,30,34`; `ExceptionService.php:123`). Repo-wide grep finds **no writer** setting `status='late'` on `asab_shifts` — no scheduled command, no on-read derivation comparing `now()` to `BrandShiftConfig` windows. The legacy `Modules/Shift/app/Console/AutoEndOverdueShiftsCommand.php` operates on legacy cashier-shift tables, never `asab_shifts`. Consequence: `live()`'s `overdue` array is always empty and the banner «انتهى وقت الشفت — لم يُغلق الصندوق بعد» can never render.
2. **Close creates a pipeline operation (module=shifts) — NO.** `Accountant/ShiftController::close` (L53–86) directly updates the `asab_shifts` row to `closed` and broadcasts; it never calls `OperationFactory`. `OperationFactory.php:18` already reserves the `'shifts' => 'SHF'` public-id prefix, and `PipelineService.php:20` labels the module «الورديات», but **no caller anywhere creates a `module_key='shifts'` Operation**. Therefore the meeting chain close→accountant approve/reject/return→head final approval→shift locks & next begins (SRS §7 ACC-6.4, §8 HEAD-2.5, backlog line 989) is entirely unimplemented.
3. **N shifts vs morning/evening — SCHEMA READY, API NOT.** `asab_brand_shift_configs` has `num_shifts` (default 1), `duration_hours` (default 8), `first_shift_start` (default '08:00') plus a `shifts` JSON column (migration `2026_06_05_000001` L67–75), and the branch read side already exposes `numShifts/durationHours/firstStart` (`BranchDashboardController.php:233–240`). But the only writer, `saveShiftConfig` (`AccountantCompanyController.php:363–376`), accepts **only** the prototype `morningWindow/eveningWindow/openingFloatHalalas` and stuffs them into the JSON column — the N-shift columns are never written and stay at defaults. **Decision documented:** adopt the meeting model as canonical — `numShifts` (1..4), `durationHours`, `firstShiftStart`, shifts named sequentially «الأول، الثاني، الثالث، الرابع» — and keep `morningWindow`/`eveningWindow` as accepted/emitted aliases (computed from shift 1/2) so the prototype FE keeps working.
4. **Live returns cashier phone — NO.** `present()` (`Accountant/ShiftController.php:88–103`) returns `supervisor` (name string) only. `asab_shifts` has no cashier link — `openShift` validates `cashierEmpNumber` then drops it (`BranchCompanyController.php:267–278`). `asab_employees` has **no phone column** (migration `2026_06_02_000001` L218–232; `storeEmployee` validates `phone` but `Employee::$fillable` lacks it, so it is silently discarded). `AsabUser.phone` exists (`AsabUser.php:23`) but is never joined into shift payloads. The ACC-6.3 contact modal (tel: / wa.me/966…) has no data source.
5. **Cash diff feeds employee ledger — NO.** Close stores `variance` on the shift row only. The only `EmployeeMovement::create` sites are `InventoryReconciliationService.php:121`, `SalesVarianceService.php:46`, and manual `Accountant/EmployeeController.php:70` — none references shifts. The SRS category «خصم فرق كاش» (§4.5 movement vocabulary, ACC-7.4 "cash gaps") has no writer. No allocation endpoint exists for shift cash gaps (unlike sales variance, which has `SalesVarianceService`).

## 3. Gaps
1. **ACC-6.4 / HEAD-2.5 approval chain** → shift close bypasses the operations pipeline: no `module_key='shifts'` Operation, no accountant approve/reject(reason)/return, no head final approval, no "shift locks & next begins". → This is the meeting's core shift requirement; without it shifts never appear in the inbox/head screens and the SHF- prefix is dead code.
2. **ACC-6.2 late detection** → no process marks `status='late'` when the configured window end passes with the shift still open. → Live tab's late banner and the `shift_unclosed`/overdue surfaces silently show nothing; accountants can't see unclosed registers.
3. **ACC-6.1 KPIs** → no endpoint computes: open now · closed today · today's sales · cash gaps needing review. → FE has nothing to bind the four stat tiles to.
4. **ACC-6.3 contact modal** → no cashier identity persisted on shift, no phone on `asab_employees` (dropped in `storeEmployee` too), no phone in any shift payload. → tel:/wa.me links impossible.
5. **§4.4 meeting shift-config model** → writer only supports morning/evening; `num_shifts/duration_hours/first_shift_start` never written; float default is 0 not 500; window strings unvalidated. → Brands running 3–4 shifts can't be configured; late detection (gap 2) has no reliable windows to compare against.
6. **ACC-7.4 «خصم فرق كاش»** → close variance never posts to the employee ledger and there is no allocation flow for shift gaps. → Cash shortages are recorded but never charged; contradicts the meeting rule that gaps land on the employee account.
7. **ACC-6.2 history/Excel shift type** → `asab_shifts` has no `shift_type` (صباحي/مسائي / sequential name) column; history rows and export lack it; history has no date-range filter. → History table and Excel can't show the SRS columns.
8. **Zero-trust close** → `salesSystem` (expected) comes from the request body and `close` has no already-closed guard; re-POST mutates `ended_at`/`variance` again; opening float in `cash_expected` is overwritten at close. → Expected-vs-actual can be forged and audit data corrupted by double submits.
9. **Assignment-scope bypass on export** → `ExportService::shifts` (L248–271) applies only the tenant global scope, not `scopeToAssignedBranches`. → A brand-scoped accountant exports other brands' shifts (violates the zero-trust rule the live/history endpoints enforce; `AccountantBrandScopeTest` covers reads but not export).
10. **BRM-5.1 open-shift fidelity** → `cashierEmpNumber` discarded; opening float not defaulted from brand config (500). → Live cards can't show the cashier; the "default 500" UX requires FE hardcoding.
11. **Live data feed** → `orders_count`/`sales_amount` have no writer (no MOB-1.6 bridge from legacy cashier shifts/POS). → Live "orders so far / expected sales" are permanently 0. (Bridge itself may land with mobile workstream, but T08 must at least expose an internal update path.)
