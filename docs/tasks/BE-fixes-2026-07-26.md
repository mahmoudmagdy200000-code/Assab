## 1. مصفوفة الموديولات للمحاسب (ADM-3.3) — كانت متعلّقة

**البلاغ:** شاشة المستخدمون بتعرض «0 مطعم · 0 صلاحية» للمحاسب، والمصفوفة بتعرض **UUID** بدل اسم المطعم وكل الخلايا «—» (0/9).

**السبب الجذري (3 حاجات، مش واحدة):**

| # | السبب | كان فين |
|---|---|---|
| 1 | **مافيش تخزين لكل (محاسب، مطعم)** — الموديولات كانت لستة واحدة مسطّحة على `asab_user_roles.module_keys`، فتعديل مطعم = تعديل كل المطاعم، والقراءة مش ممكنة لكل صف | `DistributionController::restaurantModules` (LIMITATION موثّقة) |
| 2 | **الأسماء مش في الشكل اللي المصفوفة تقدر تفهرسه** — `allRestaurants` IDs بس، و`accModules` مفهرسة بـ **الاسم** مش الـ id | `DistributionController::index` |
| 3 | **قايمة المستخدمين بترجّع `restaurant_ids` الخام** للمحاسب، وهي **فاضية بالتصميم** (المحاسب على مستوى البراند) → «0 مطعم» | `UserController::present` |

**كمان باج أمني في نفس المسار:** الحفظ القديم كان **يضيف المطعم لـ `restaurant_ids`** ويحوّل `scope` إلى `restaurant` — يعني حفظ صلاحيات كان **يوسّع نطاق بيانات** المحاسب. اتشال.

### الإصلاح

- جدول جديد `asab_accountant_restaurant_modules` = خلية لكل (محاسب × مطعم)، `unique(accountant_id, restaurant_id)`.
- `asab_user_roles.module_keys` **بقى مرآة للاتحاد (UNION)** لكل خلايا المحاسب — عشان `ResolveTenant` و`AuthService` بيقروا اللستة المسطّحة دي وماينفعش سلوكهم يتغيّر.
- اللستة القديمة **بتتحوّل لخلايا** أول مرة الأدمن يعدّل (مش بتتلغي) — فالصلاحية الحالية مابتتغيّرش.
- لما **تغطية المحاسب تتغيّر** (نقله لبراند تاني) الاتحاد بيُعاد حسابه: خلية مطعم خرج من تغطيته **بتتوقّف عن المنح** (الخلايا نفسها بتفضل محفوظة، فلو رجّعته للبراند ترجع المصفوفة زي ما بناها الأدمن).
- الخلايا برّه تغطية المحاسب **مرفوضة** بـ 422 مع السبب، مش بتتحوّل لتعيين ضمني.

### الـ endpoints

**`GET /api/v1/admin/accountants/{accId}/modules`** ← ده اللي الشاشة كانت ناقصاها

```json
{
  "accountantId": "u-uuid",
  "accountantName": "محمد محاسب",
  "headId": "h-uuid",
  "brands": ["b-uuid"],
  "moduleCatalog": [{ "key": "sales", "labelAr": "المبيعات", "labelEn": "Sales", "icon": "💰" }],
  "restaurants": [
    {
      "restaurantId": "r-uuid",
      "restaurantName": "الخرج",          // ⭐ اعرض ده مش الـ id
      "brandId": "b-uuid",
      "brandName": "حية عنب",
      "modules": ["sales", "expenses"],   // ⭐ الخلايا المفعّلة في الصف
      "moduleCount": 2,
      "availableModules": ["sales", "expenses"],  // باقة البراند (إرشادي — للتظليل فقط)
      "total": 9,
      "isExplicit": true
    }
  ],
  "totals": { "restaurants": 5, "modulesGranted": 3, "modules": 9 },
  "reason": null
}
```

- `moduleCatalog` = أعمدة المصفوفة التسعة بترتيبها ولابلاتها العربية. **ابنِ الأعمدة منه** ولا تكتبها في الفرونت.
- `reason: "NO_COVERED_RESTAURANTS"` مع `restaurants: []` = المحاسب **مش مخصّص لبراند** (أو براند مالوش مطاعم). ده السبب الحقيقي للشاشة الفاضية — اعرض رسالة «عيّن براند للمحاسب أولاً» بدل جدول فاضي.

**الحفظ — خليّة واحدة:**
`PUT /api/v1/admin/accountants/{accId}/restaurants/{restaurantId}/modules` · body `{ "modules": ["sales","waste"] }`
→ `200 { accountantId, restaurant, restaurantName, modules, moduleCount, total }`

**الحفظ — كل المصفوفة:**
`PUT /api/v1/admin/accountants/{accId}/modules`
```json
{ "restaurants": [
  { "restaurantId": "r1", "modules": ["sales"] },
  { "restaurantId": "r2", "modules": ["inventory","cash"] }
] }
```
→ `200 { accountantId, moduleCatalog, restaurants: [ …نفس شكل صفوف الـ GET… ] }`
المطاعم اللي مش في الـ body مابتتغيّرش. **id واحد برّه التغطية يرفض الحفظ كله** (مافيش نصف مصفوفة).

**البديل الحبّة-حبّة (نفس السلوك):** `POST /api/v1/admin/distribution/assign-modules` · `{ accountantId, restaurantId, modules }` → بقى يرجّع صف المصفوفة (كان 204).

**الأخطاء:**

| الحالة | الرد |
|---|---|
| مطعم برّه تغطية المحاسب | `422 RESTAURANT_NOT_ASSIGNED` + `error.details.restaurants` |
| مفتاح موديول مش من التسعة | `422 VALIDATION_ERROR` |
| المستخدم مش محاسب | `404 NOT_FOUND` |

## 2. الأصول الثابتة — «برفعها، أعمل refresh، مش متحفظة»

**السبب الجذري:** `asab_assets.company_id` عمود **NOT NULL**، والمستورد كان بياخده من `branches.asab_company_id`، وهو **NULL** في الفروع اللي مادخلتش أعمدة الهيكل (فروع قديمة أو أنشئت من مسار مالوش ربط). أمين النظام مالوش شركة خاصة به، فـ **كل صف** كان يموت على القيد… والـ endpoint كان يرجّع **200** و`assetCount: 0` (وبيسرّب نص جملة `INSERT` كامل في `errors`)، فالعمود يفضل «لم يُرفع» بعد كل رفع.

**الإصلاح:**

1. **الشركة بتُحلّ عبر السلسلة** قبل أي قراءة للملف: `branch.asab_company_id` → مطعم الفرع → براند الفرع → شركة المستخدم؛ ولما تُحلّ **بتتكتب على الفرع** (backfill) عشان الشاشات الجاية تقراها مباشرة.
2. **مافيش ربط خالص** → `422 BRANCH_NOT_LINKED` («هذا الفرع غير مرتبط بشركة…») قبل الاستيراد، بدل 8 أخطاء قيد متشابهة.
3. **رفع ماحفظش ولا صف = خطأ مش نجاح** → `422 UPLOAD_FAILED` + `error.details.errors[]`. (كان `200` + `assetCount: 0`، والشاشة تقراه نجاح.) صف الحالة بيُكتب **قبل** الخطأ، فالسبب يفضل ظاهر في العمود.
4. **مافيش تسريب رسائل الـ driver** — خطأ SQL في صف بيتحوّل لرسالة عربية قابلة للتصرّف + `report()` للّوج.

**القراءة — `GET /api/v1/admin/branches/{branchId}/upload-status` (حقول جديدة):**

```json
{
  "fixedAssets": true,
  "fixedAssetsStatus": "done",          // done | failed | not_uploaded  ⭐
  "fixedAssetsCount": 12,
  "fixedAssetsFailedRows": 0,
  "fixedAssetsFailureReason": null,     // اعرضها لما status=failed
  "fixedAssetsUploadedAt": "2026-07-26T11:22:54+03:00"
}
```

`fixedAssets` لوحده مايفرّقش بين «لم يُرفع» و«رُفع وفشل» — استخدم `fixedAssetsStatus`.

**العمود كله في نداء واحد (جديد):**
`GET /api/v1/admin/brands/{brandId}/branches/upload-status`

```json
{
  "brandId": "b-uuid",
  "branches": [
    { "branchId": "…", "branchName": "فرع الخرج 1", "restaurantId": "…", "restaurantName": "الخرج",
      "fixedAssetsStatus": "done", "fixedAssetsCount": 12, "fixedAssetsFailureReason": null, "uploads": [ … ] }
  ],
  "totals": { "branches": 3, "uploaded": 1, "failed": 0 }
}
```

> **للفرونت:** ده اللي بيمنع رسم العمود كله «لم يُرفع» — بدل نداء لكل فرع. الرفع نفسه لسه **لكل فرع**: `POST /api/v1/admin/branches/{branchId}/upload/fixed-assets` (أو `uploads/`).

## 3. لوجين الموبايل — «The identifier field is required»

**السبب الجذري:** التطبيق بيبعت قيمة الحساب باسم `email` (اللابل «Registered»)، والـ requests بتطلب `identifier`. الإصلاح القديم اتطبّق على **مدير الفرع فقط** (trait جوّه موديول BranchManagers)، فالمورد المُنشأ من الداش بورد لسه بياخد 422 على حقل مليان.

**الإصلاح:** الـ trait اتنقل لـ `App\Http\Requests\Concerns\NormalizesIdentifier` واتطبّق على **17** request في 4 موديولات (مورد، مالك علامة، كاشير، مدير فرع): لوجين، أول لوجين، OTP إرسال/تحقق، واستعادة الباسورد. الأسماء المقبولة: `email` · `phone` · `username` · `login` · `registered` · `registered_email`. الطلب اللي فيه `identifier` **مايتغيّرش**.

تست `MobileLoginIdentifierAliasTest` فيه مسح (sweep) بيفشل لو انضاف request جديد بيطلب `identifier` من غير الـ trait — عشان الحفرة دي ماتتفتحش تاني.

## 4. «activate Account» بترجّع Unauthenticated

**البلاغ:** بعد أول لوجين ناجح، شاشة «activate Account» (كلمة سر جديدة + تأكيد) بترجّع **Unauthenticated.**

**السبب الجذري:** الشاشة مافيهاش غير خانتين باسورد، و endpoint التفعيل كان **جوّه `auth:sanctum`** — فأي build مابيرفقش توكن أول-لوجين كـ Bearer يوصل لطريق مسدود مايقدرش يخرج منه. تأكّدت من الباك اند: **بالتوكن → 200**، فالمشكلة إن الطلب واصل من غير توكن.

**الإصلاح:** التفعيل بقى يقبل **أي إثبات** للاعتماد اللي الأدمن أصدره (`App\Services\FirstLoginActivationResolver`):

| الإثبات | الشكل |
|---|---|
| توكن أول-لوجين في الهيدر | `Authorization: Bearer <token>` (التعاقد الأصلي — لسه شغّال) |
| نفس التوكن في الـ body | `{ "token": "…" }` |
| الباسورد الافتراضي تاني | `{ "identifier": "…", "default_password": "…" }` (نفس شكل شاشة تفعيل الكاشير؛ و`email`/`phone` بيتطبّعوا لـ `identifier`) |

مافيش **أي** تفعيل بدون واحد منهم → `401`. والحسابات المفعّلة أصلاً `400`، والموقوفة `403`. المسارات throttled.

اتطبّق على **3 موديولات** لأن نفس الشاشة بتخدمهم:
- `POST /api/v1/supplier/auth/password/reset/first-login`
- `POST /api/v1/branch-manager/auth/reset-password-first-login`
- `POST /api/v1/brand-owner/auth/reset-password-first-login`

> **للفرونت:** أسهل مسار = ابعت `identifier` + `default_password` مع الباسورد الجديد؛ مش محتاج تحفظ التوكن بين الشاشتين. لو بتحفظه، ابعته زي ما هو في الهيدر (أو في الـ body لو أسهل).

## 5. بورتال المورد — «تعذر الاتصال بالخادم» عند إضافة صنف

**السبب الجذري:** كل مسارات بورتال المورد (`/api/v1/asab/supplier/*`) **جوّه feature flag**:

```php
// config/features.php
'asab_supplier_portal' => (bool) env('FEATURE_ASAB_SUPPLIER_PORTAL', false),
```

الفلاج مكان مش موجود في `.env` → القيمة `false` → المسارات **مش بتتسجّل من الأصل** (مش 403، مسار غير موجود) → الفرونت بيقرا الرد كـ فشل اتصال ويعرض «تعذر الاتصال بالخادم». الكود نفسه سليم ومتّست (`AsabSupplierPortalTest` بيشغّل الفلاج ويختبر list/store/patch/toggle/delete/export).

**الإصلاح:** اتحطّ في `.env`:

```
FEATURE_ASAB_SUPPLIER_PORTAL=true
```
\+ `php artisan config:clear && php artisan route:clear` (المسارات متعلّقة بالكونفيج، فالكاش لازم يتفضّى). اتأكدت إن `route:list --path=asab/supplier` بقى بيطلّع الـ 13 مسار.

> **ops:** نفس المتغيّر لازم يتحط في **prod** — `.env.example` لسه `false` (القيمة الافتراضية اللي اتفق عليها في الاجتماع «إخفاء البورتال»). لو المطلوب يبقى مفتوح لكل البيئات، غيّروا الـ default في `config/features.php` وأنا أعمله.

**ملاحظتان في نفس الشاشة (مش باج النهاردة — للعلم):**

1. **وحدة السعر:** `asab_supplier_items.price` عدد صحيح، والـ endpoint بيقبل `price`/`priceHalalas` وبيرجّع نفس الرقم في الاتنين. يعني اللي بتبعته بيرجع زي ما هو — بس باقي النظام (المشتريات/الجسور) بيتعامل مع الأسعار **بالهللة**. لو الشاشة بتبعت 2000 وهي تقصد 2000 ر.س، الرقم المخزّن هيتقرا 20.00 ر.س في أي حساب بيقسّم على 100. القرار محتاج تثبيت: الفرونت يبعت هللات (200000)، أو نضيف حقل `priceSar` صريح.
2. **الأصناف دي مش موصولة بموبايل المشتريات:** البورتال بيكتب في `asab_supplier_items`، وبيكرز الموبايل بتقرا من `supplier_items` (موديول Purchase). يعني الصنف اللي المورد يضيفه من البورتال مش هيظهر لمدير الفرع/موظف المشتريات في التطبيق لحد ما نبني الجسر (زي ما عملنا في BUG-9 لرفع الكتالوج).
