# إصلاح 2026-08-04 — كتالوج الأصناف لمدير المشتريات

**الملاحظة:** من شاشة «الأصناف» لا يمكن إضافة صنف جديد — لا بـ«إضافة صنف» ولا
بالإكسيل — والرسالة: **«المستخدم غير مرتبط بشركة»**.

---

## السبب

الرسالة تأتي من `ResolveTenant` بالكود `WRONG_TENANT` (403). حساب مدير المشتريات
في اللقطة حساب **منصّة** (`company_id = NULL`) — يشتري لعصب لا لشركة واحدة، وهذا
مسموح ومقصود. لكن كتابة الكتالوج كانت متاحة على سطح الشركة فقط:

```
POST /api/v1/company/me/procurement/items      ← ممنوع على حساب المنصّة
```

و`ResolveTenant` يغلق مسار `api/*/company/*` كاملًا أمام أي حساب بلا شركة (وهذا
صحيح: عشرات المتحكمات هناك تقرأ `company_id` مباشرة وتعتبر الـ NULL «بلا فلترة»).
أما سطح المنصّة `/api/v1/procurement/*` فكان يحتوي **قراءة فقط**:
`GET items` — بلا إضافة ولا تعديل ولا حذف ولا رفع إكسيل. فالشاشة تعرض أزرارًا لا
مقابل لها في الـ API.

## ما تم

### 1) كتابة الكتالوج على سطح المنصّة

```
GET    /api/v1/procurement/items                      (كما هو)
POST   /api/v1/procurement/items                      ← جديد
PATCH  /api/v1/procurement/items/{id}                 ← جديد
DELETE /api/v1/procurement/items/{id}                 ← جديد
GET    /api/v1/procurement/items/{id}/price-history   ← جديد
GET    /api/v1/procurement/items/template?format=xlsx|csv   ← جديد
POST   /api/v1/procurement/items/import               ← جديد (multipart: file)
```

نفس المتحكم الذي يخدم سطح الشركة، مع قاعدة ملكية صريحة:

- حساب **شركة** يكتب صفوف شركته.
- حساب **منصّة** يكتب الصفوف بلا شركة (`company_id IS NULL`) فقط — تعديل صنف
  يخص شركة يرجع 404، فلا كتابة عابرة للمستأجرين.

> ملاحظة تقنية: `where('company_id', null)` في SQL لا يطابق شيئًا، لذلك كان حساب
> المنصّة يستطيع الإنشاء ثم لا يستطيع التعديل أبدًا. صار `whereNull`.

المسارات نفسها أُضيفت أيضًا تحت `company/me/procurement/` (`items/template`،
`items/import`) لحسابات الشركة.

### 2) الرفع بالإكسيل

نفس قالب أصناف بوابة المورد:

| الصنف | الرمز | الوحدة | السعر (ر.س) | الحد الأدنى | الحد الأقصى | مدة التحضير (يوم) | الفئة | متاح |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

- السعر في الملف بالريال ويُخزَّن بالهللات.
- **idempotent**: المطابقة على «الرمز» وإلا على «الصنف» داخل نفس الكتالوج، فإعادة الرفع تُحدِّث ولا تُكرِّر.
- الرد: `{ "itemCount": 12, "errors": [{ "row": 4, "message": "…" }] }`، و422 `UPLOAD_FAILED` إن لم يُحفظ أي صف.

### 3) وحدة السعر (مهم للفرونت)

الحقل في الشاشة «آخر سعر (ر.س)» بينما `lastPriceHalalas` بالهللات — إرسال 500
كان يُخزَّن 5.00 ر.س. أُضيف حقل صريح:

```jsonc
// POST/PATCH — أرسل أحد الثلاثة
{ "lastPriceSar": 500 }          // ← بالريال (الأنسب للحقل الظاهر)
{ "lastPriceHalalas": 50000 }    // ← بالهللات (كما كان)
{ "defaultPriceHalalas": 50000 } // ← مرادف قديم

// كل الردود وقوائم الأصناف تحمل الاثنين
{ "lastPriceHalalas": 50000, "lastPriceSar": 500 }
```

### 4) إصلاحان جانبيان ظهرا أثناء التنفيذ

- `asab_procurement_item_prices.company_id` كان `NOT NULL`، فأول تغيير سعر على صنف منصّة كان يسقط على القيد → صار nullable (ترحيل جديد).
- سجل الأسعار لحساب المنصّة كان يرجع فارغًا (نطاق المستأجر يفشل مغلقًا) → `ProcurementItemPrice` صار `platformVisible`, مع إبقاء الفلترة الصريحة على `company_id IS NULL`. وأُضيف ترتيب ثانوي بالـ id حتى لا يظهر السعر الأقدم عند تعديلين في نفس الثانية.
