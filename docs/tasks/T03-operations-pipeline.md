## 2. Answers to critical checks

1. **origin / source_module / erp_posted on `asab_operations` — PARTLY YES.** Migration `Modules/Admin/database/migrations/2026_06_02_000001_create_asab_layer_tables.php`: `origin` string(16) default `'mobile'` (line 176), `source_module` string(32) nullable legacy-module pointer (line 170), `erp_posted` boolean default false (line 194) + `erp_batch_id`/`erp_posted_at` (195–196). `erp_posted` is genuinely stamped by `ErpBatchService` (ErpBatchService.php:50–52) and consumed by the pipeline funnel (PipelineService.php:31). Values in use: `'mobile'` (OperationFactory.php:38), `'system'` for corrections (OperationService.php:132). **BUG:** the procurement flow never sets the column — `ProcurementCompanyController@storeOrder` puts `'origin' => 'procurement'` inside the **payload JSON** (ProcurementCompanyController.php:45) while `OperationFactory::createFromUpload` hardcodes the column to `'mobile'` (OperationFactory.php:38). So سير المشتريات ops are stored as «📱 تطبيق الفرع». No `in:mobile,procurement,system` validation anywhere; no Arabic labels returned (raw key only, OperationController.php:233).
2. **§5.2c daily rollup state machine — MISSING ENTIRELY.** `PipelineController@overview` (PipelineController.php:19–22 → PipelineService.php:27–56) is a whole-history status funnel; `@aggregation` (PipelineService.php:59–89) is a per-module count/amount grid. Neither groups by branch+day nor derives `empty→incomplete→ready_consolidation→consolidated→ready_erp→exported→erp_imported`. Repo-wide grep for those keys (and Arabic labels «جاهز للتجميع», «مُجمَّع», «جاهز لـ ERP») returns nothing. All derivation inputs exist on the model (`status`, `erp_posted`, `branch_id`, `operation_date`), so this is a pure computed-service + endpoint build (SRS explicitly: "implement as computed service, not stored-only").
3. **Rejection reasons fixed enum — NO.** `OperationController@reject` validates `reason => required|string|max:500` free text (OperationController.php:73); `OperationService::reject` stores it verbatim into `reject_reason` (500-char column). No canonical list constant, no `lookups/rejection-reasons` endpoint (LookupController has brands/restaurants/branches/users/suppliers/items/employees/modules/exceptions only), no sales-specific extension («تقرير POS مفقود، كشف البنك غير مرفق»). The seeder happens to use one SRS phrase («فاتورة مفقودة أو غير واضحة», AsabOperationSeeder.php:35) but nothing enforces the list.
4. **final-approved immutability — ENFORCED in the pipeline service, with one leak.** Enforced: `approve` asserts `pending` (OperationService.php:25→182–193, 409), `reject` throws `OP_ALREADY_FINAL` 409 for final/rejected (OperationService.php:52–54), `finalApprove` asserts `approved` so double-final is 409 (OperationService.php:86); `AccountantController@reconciliation` refuses final ops with 409 (AccountantController.php:140–142). **Leak:** `ProcurementCompanyController@updateOrder` (`PATCH /company/me/procurement/orders/{id}`) accepts a `status` field valid for any of the 4 statuses and writes it with `$op->update()` — no current-status guard — so a `final-approved` purchases op can be flipped back to `pending` and its payload rewritten (ProcurementCompanyController.php:56–74). No model-level guard on `Operation` either.
5. **Clarification-request («طلب توضيح») — MISSING.** No route in routes/api.php, no controller method, zero grep hits for `توضيح`/`clarification` under `Modules/Admin`. The `correction` endpoint does NOT cover the semantics: correction spawns a new linked pending operation (origin `system`) — the SRS action is non-terminal on the *same* operation (op stays `pending`, submitter is asked for info). Needs a new endpoint (audit step + notification to `submitted_by_id`, no status change).

## 3. Gaps

- **G1 · §5.2c** → No branch/day rollup state machine (endpoint #12) → the main dashboard's core aggregate widget (labels «لا بيانات / غير مكتمل / جاهز للتجميع / مُجمَّع / جاهز لـ ERP / مُصدَّر / مُستورَد في ERP ★») has no data source; consolidation/ERP-readiness cannot be shown per branch-day. Biggest T03 gap.
- **G2 · §5.2b** → Procurement-origin ops stored with column `origin='mobile'` (payload-only `'procurement'`); no enum validation; existing rows mislabeled → origin badge («🛒 سير المشتريات» vs «📱 تطبيق الفرع») will be wrong for every dashboard-created purchase order; rollup/report filters by origin impossible until backfilled.
- **G3 · §5.4** → Rejection reason is free text; no fixed generic list («بيانات غير مكتملة، فاتورة مفقودة أو غير واضحة، تناقض في المبالغ، فرق في الكميات، تاريخ غير صحيح، مورد غير معتمد، أخرى») nor sales additions («تقرير POS مفقود، كشف البنك غير مرفق»); no lookup endpoint → FE must hardcode; analytics on rejection causes impossible; SRS says "fixed lists, required on reject".
- **G4 · §5.1 (🔒 locked)** → Immutability bypass via `ProcurementCompanyController@updateOrder` status write (ProcurementCompanyController.php:61–74) → a locked accounting record can be reopened/edited after head sign-off; violates «معتمد نهائياً — مُغلق» and the master-plan invariant (409 expected).
- **G5 · ACC-0.5/ACC-1.4 (uses §5.1 non-terminal action)** → «طلب توضيح» endpoint absent → accountant inbox action has no backend; rejections get used as a workaround, wrongly kicking ops off-pipeline.
- **G6 · master-plan cross-cutting + §5.1/5.2b/5.3** → `present()` and pipeline payloads return bare enum keys without Arabic labels (only PipelineService stages carry `labelAr`) → FE re-implements label maps per screen; contract says every status is a `{key, labelAr}` pair.
- **G7 · zero-trust** → operations export (ExportService.php:412) and pipeline overview/aggregation (PipelineService.php:95–102) skip `scopeToAssignedBranches` → branch-scoped accountants see/export company-wide data. Index/show/approve paths already scope correctly.
- **G8 · robustness** → `public_id` generation is `count()+1` (OperationFactory.php:69–75, OperationService.php:148–154): concurrent creates or a soft-deleted row shrinking the count collide with the `unique` index → unhandled QueryException (500) instead of a domain error.

## 5. Tests required

Pest feature tests (SQLite in-memory; seed via `AsabOperationSeeder` patterns):

1. **Lifecycle happy path**: create pending op → accountant approve (200, status `approved`, step row written) → head final-approve (200, `final-approved`, `final_approved_at` set) → audit-trail returns submit/approved/final with `isTerminal` on last.
2. **State-machine 409s**: approve a non-pending op → 409 `OP_NOT_PENDING`; final-approve a pending op → 409 `OP_NOT_APPROVED`; reject a final op → 409 `OP_ALREADY_FINAL`; double final-approve → 409.
3. **Locked immutability**: after final-approve — reject → 409; `PATCH /company/me/procurement/orders/{id}` status write → 409 (T03.6); reconciliation PATCH → 409 (already enforced, keep regression).
4. **Reject flow**: reject requires `reason` (422 when absent); valid enum reason stored + submitter notification created; sales op accepts «تقرير POS مفقود», expenses op rejects it (422) (after T03.4).
5. **Conditional final-approve**: `isConditional:true` without `conditionalNote` → 422; with note + conditions → step meta contains conditions.
6. **Correction**: creates linked pending op (`corrective_ref_id`, `is_correction`, `origin='system'`, `match='review'`); response returns linkage ids; steps written on both ops.
7. **Bulk approve**: mixed ids (pending, already-approved, other-tenant, unknown) → only pending in caller's scope approved; failed array carries codes; out-of-scope id NOT approved (zero-trust).
8. **Role denial**: branch-role token → approve/reject/final-approve/bulk-approve/export → 403; accountant → final-approve → 403; head allowed everywhere.
9. **Tenant isolation**: company-B accountant cannot `show`/`approve` company-A op (404); branch-scoped accountant cannot see other-branch ops in index, export, pipeline/overview, daily-rollup (after T03.7).
10. **Daily rollup derivation** (T03.2): six scenarios — no ops→`empty`; any pending→`incomplete`; all approved→`ready_consolidation`; approved+final mix→`consolidated`; all final not posted→`ready_erp`; all final + `erp_posted`→`exported`; response carries `{key,labelAr,subLabelAr,step}` verbatim.
11. **Origin**: dashboard procurement order stores column `origin='procurement'`; `?origin=` filter works; backfill migration converts payload-origin rows (guard `DB::getDriverName()` for sqlite).
12. **Clarification** (T03.5): status unchanged, step + notification created, 409 on final op.
13. **public_id race** (T03.8): soft-delete highest op then create → no duplicate-key exception.
14. **Export**: `GET /v1/operations/export?moduleKey=purchases&format=csv` → 200 file response; branch-scoped accountant's file excludes other branches.

## 6. FE wiring notes

- **Canonical paths**: `/v1/operations/*` and `/v1/pipeline/*` are canonical. The `/v1/company/me/operations*` copies (routes/api.php:622–633) are accountant-surface aliases to the *same* handlers — FE should call the canonical path; document the aliases as deprecated-equivalent. `GET /operations/export` is registered **before** `/operations/{id}` — never treat `export` as an id.
- **Enums (return verbatim, keys stable)** — status: `pending` قيد المراجعة / معلق · `approved` تمت الموافقة — «معتمد - مرحلة 1» · `rejected` مرفوض · `final-approved` معتمد نهائياً 🔒 «مُغلق». Origin: `mobile` 📱 تطبيق الفرع · `procurement` 🛒 سير المشتريات · `system` ⚙ استيراد النظام. Match: `exact` متطابق ✓ · `review` يحتاج مراجعة · `diff` فرق ⛔ (code uses exactly `exact|review|diff`; SRS aliases `needs-review`/`qty-diff` are NOT emitted). Rollup: `empty` لا بيانات · `incomplete` غير مكتمل · `ready_consolidation` جاهز للتجميع · `consolidated` مُجمَّع · `ready_erp` جاهز لـ ERP · `exported` مُصدَّر · `erp_imported` مُستورَد في ERP ★ (مرحلة مستقبلية). Stage ids in audit-trail: `submit|review|approved|final|erp|rejected|reports` with icon field from backend.
- **Until T03.1 ships**, all enum fields are bare keys — FE must not depend on server labels yet; after T03.1 they become `{key, labelAr}` objects (document the exact cut-over in the FE doc).
- **Amounts are integer halalas** everywhere (`amount`, `totalAmountHalalas`); FE divides by 100 for ر.س display.
- **Conditional approval**: there is no `/conditional-approve` endpoint — it's `final-approve` with `isConditional:true` + `conditionalNote` (+optional `conditions[]`). Response op carries `isConditional`.
- **Correction response is a linkage object** (`originalOperationId`, `correctionOperationId`, `publicId`, `status`, `createdAt`), NOT the full operation — FE must re-fetch if it needs the new op body. Accepts both `{reason, notes?, correctedFields?}` and legacy `{correctionReason, amount, diffNote}`.
- **Screen mapping**: `pipeline/overview` → «دورة حياة العملية» funnel widget (stages м1–م5 + rejected; م6 تقارير ERP is future/read-only per footer «م1–م5: مدارة بواسطة آلة الحالة…»); `modules/aggregation` → module aggregation grid (8 modules with Arabic labels from backend); `pipeline/daily-rollup` (new) → main-dashboard branch/day state chips; `operations` index → accountant inbox table (summary block feeds the 4 KPI counters); `audit-trail` → operation timeline drawer.
- **Errors**: all domain failures use the unified envelope with `errorCode` (`OP_NOT_PENDING`, `OP_NOT_APPROVED`, `OP_ALREADY_FINAL`) at 409; validation at 422 `VALIDATION_ERROR`; out-of-scope/tenant-mismatch reads as 404 `NOT_FOUND` (never 403 — don't leak existence).
- **Id flexibility**: `{id}` accepts either uuid or `public_id` (e.g. `OPS-2401`) on show/approve/reject/final-approve/correction/audit-trail.
